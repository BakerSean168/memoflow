## P1-1：`expectedVersion` 没有形成强制的端到端命令契约

更新和删除 schema 都把 `expectedVersion` 声明为 optional（[`schedule-requests.ts:39`](../../packages/contracts/src/modules/schedule/api/requests/schedule-requests.ts:39)、[`schedule-requests.ts:127`](../../packages/contracts/src/modules/schedule/api/requests/schedule-requests.ts:127)），application port 和 service 同样接受 optional 版本（[`schedule.application.port.ts:38`](../../packages/schedule/src/server/application/schedule.application.port.ts:38)、[`schedule-event-application-service.ts:73`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:73)、[`schedule-event-application-service.ts:145`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:145)）。这使调用者仍可省略版本，service 会读取当前版本后自行作为 CAS 条件，语义等价于“以服务端刚读到的版本覆盖”，不能表达客户端所编辑的 revision。

删除链路甚至不可传递新增字段：HTTP DELETE 路由既未声明 body schema，也只调用 `controller.delete(id, ctx)`（[`schedule-event.routes.ts:153`](../../packages/schedule/src/api/schedule-event.routes.ts:153)）；Electron handler 只接收 id（[`electron/index.ts:131`](../../packages/schedule/src/electron/index.ts:131)）；HTTP/IPC adapters 和两层 client port 的 `deleteSchedule` 都只有 id（[`schedule-event-http.adapter.ts:58`](../../packages/schedule/src/infrastructure-client/adapters/http/schedule-event-http.adapter.ts:58)、[`schedule-event-ipc.adapter.ts:50`](../../packages/schedule/src/infrastructure-client/adapters/ipc/schedule-event-ipc.adapter.ts:50)、[`schedule-event-api-client.port.ts:33`](../../packages/schedule/src/application-client/ports/schedule-event-api-client.port.ts:33)、[`schedule-client.port.ts:22`](../../packages/schedule/src/application-client/schedule-client.port.ts:22)），UI 也仅发送 id（[`useScheduleCalendar.ts:61`](../../packages/app-vue/src/modules/schedule/composables/useScheduleCalendar.ts:61)）。因此真实客户端删除永远不会收到 stale-version conflict。

关闭条件：update/delete 的公共命令 schema、application/client ports、HTTP OpenAPI、IPC handler/adapter 和 UI 全链路要求并传递 `expectedVersion`；缺失版本必须 validation fail，不能在 service 内补成当前版本；冲突 Result 必须稳定携带结构化 `currentVersion`，并有 HTTP 与 IPC contract test。

## P1-2：PowerSync 组合根绕过 CAS、version、事务和 durable outbox

`PowerSyncScheduleRepository.save()` 不接收/检查 `expectedVersion`；UPDATE 只按 id，既不含 identity，也不含 version，且 SET 列表没有 version（[`schedule-powersync.repository.ts:21`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:21)）。INSERT 同样未写 version（[`schedule-powersync.repository.ts:59`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:59)），mapper 的 persistence shape 也没有 version（[`powersync-schedule.mapper.ts:48`](../../packages/schedule/src/server/infrastructure/adapters/powersync/mappers/powersync-schedule.mapper.ts:48)）。delete 只按 `id + identity_id`，忽略传入的 expectedVersion（[`schedule-powersync.repository.ts:100`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:100)）。

更严重的是，PowerSync 的 `withTransaction()` 只是直接执行 callback，并未调用数据库事务（[`schedule-powersync.repository.ts:144`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:144)）；它也没有 rebuild outbox 方法。application service 把 `withTransaction` 和全部 outbox 方法设计成 optional，并在缺失时继续执行（[`i-schedule-repository.ts:69`](../../packages/schedule/src/server/domain/repositories/i-schedule-repository.ts:69)、[`i-schedule-repository.ts:92`](../../packages/schedule/src/server/domain/repositories/i-schedule-repository.ts:92)、[`schedule-event-application-service.ts:200`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:200)）。PowerSync 又是显式可用的 production composition root（[`powersync.ts:41`](../../packages/schedule/src/server/infrastructure/powersync.ts:41)），所以不是测试-only adapter。

关闭条件：所有可启动组合根必须提供强制 conditional-write、真实 transaction runner 和 durable rebuild outbox 能力；无能力时组合根 fail-fast。PowerSync 必须用真实数据库 affected-row 证明 `identity_id + id + version` CAS，并用故障注入证明 aggregate/projection/outbox 同 commit 或按明确的 offline durable protocol 收敛，不能保留 inline transaction fallback。

## P1-3：rebuild worker 没有生产生命周期，失败后也不可重试/不可重建

`ScheduleRebuildWorkerService` 只出现在自身文件和 W5 单测中，没有在 Prisma module、PowerSync module、API/desktop bootstrap 或 runtime contribution 中实例化/启动；`createSchedulePrismaModule()` 只是原样透传外部 runtime contributions（[`prisma.ts:29`](../../packages/schedule/src/server/infrastructure/prisma.ts:29)）。因此进程重启后没有 worker 自动扫描持久化 outbox，计划要求的“删除后 worker 重启重建”在生产中不存在。

状态机也不是 retryable。worker 只 fetch `status = pending`（[`schedule-prisma.repository.ts:225`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:225)），任何异常都把记录标成 `failed`（[`schedule-rebuild-worker-service.ts:62`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:62)、[`schedule-prisma.repository.ts:240`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:240)），后续扫描永远不再读取。记录没有 next-attempt/claim/lease owner；worker 收到的 `guard` 从未调用 `ensureHeld()`，处理中即使 lease 丢失也会继续写（[`schedule-rebuild-worker-service.ts:37`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:37)）。

关闭条件：把 worker 作为 module-owned runtime 接入 API/desktop 需要的组合根，启动扫描并可安全停止；实现 pending/processing/retry/failed/completed 的可恢复状态机、claim token/超时回收/退避与最大尝试策略；每批及关键写前检查 lease guard；用真实持久化测试证明进程在 dequeue 前、投影后、ack 前分别崩溃均可重启收敛。

## P1-4：投影写会改业务 revision、无条件覆盖并发更新，source revision 也未生效

`ScheduleConflictCacheService.refreshSchedule()` 无论投影是否变化都会调用 repository `save(schedule)`，且在有冲突时每次都调用 `markAsConflicting`（[`schedule-conflict-cache-service.ts:24`](../../packages/schedule/src/server/application/services/schedule-conflict-cache-service.ts:24)）。`markAsConflicting`/`clearConflicts` 会增加 aggregate version（[`calendar-entry.ts:268`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:268)），随后 save 未带 expectedVersion；Prisma 分支因此走整行 upsert（[`schedule-prisma.repository.ts:101`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:101)）。worker 若读到旧快照并与客户端更新竞争，可能把 title/time 等业务字段回写为旧值；重复 rebuild 即使投影相同也会继续增加 version，并非幂等。

command revision 自身也不一致。每个字段 mutation 都单独增加 domain version（例如 title 与 reschedule 分别递增，[`calendar-entry.ts:292`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:292)、[`calendar-entry.ts:318`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:318)），但 Prisma CAS 永远落为 `expectedVersion + 1`（[`schedule-prisma.repository.ts:66`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:66)）；outbox 却记录内存 aggregate 的 `schedule.version`（[`schedule-event-application-service.ts:129`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:129)）。一次多字段更新即可令 outbox `sourceRevision` 与数据库 revision 不同。worker 从未读取或比较 `item.sourceRevision`，所以 stale item 仍会重建并覆盖新状态（[`schedule-rebuild-worker-service.ts:50`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:50)）。

关闭条件：将 conflict projection 与业务 aggregate revision/字段隔离，或提供只更新投影列且带 projection/source revision CAS 的专用 port；相同投影重复应用不得改变任何持久状态；command 一次只推进一个明确 revision；worker 必须拒绝/合并 stale source revision，并以真实 DB 测试覆盖 ack 前重复、乱序、新旧 revision 交错以及 worker/client 并发。

## P1-5：删除的外部事件不与数据库事务原子，回滚仍可留下已发布副作用

Prisma `deleteAggregate()` 在删除行后立即调用进程 event bus（[`schedule-prisma.repository.ts:187`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:187)），application service 随后才刷新冲突并写 rebuild outbox（[`schedule-event-application-service.ts:164`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:164)）。若投影或 outbox 写失败，Prisma transaction 会回滚删除，但已经发布的 delete domain event 无法回滚；消费者可在数据库仍保留事件时执行删除相关副作用。新增 fault test 只 mock outbox 并检查内存 aggregate，没有经过真实 event bus，也只覆盖 update，不覆盖 delete（[`schedule-w5-concurrency-projection.spec.ts:222`](../../packages/schedule/src/server/application/services/__tests__/schedule-w5-concurrency-projection.spec.ts:222)）。

关闭条件：delete event 必须作为同事务 durable outbox 写入，commit 后再发布；故障注入应证明 projection/outbox 任一写失败时 aggregate、conflict projection、rebuild outbox、domain-event outbox 全部回滚且没有外部事件可见。

## P2-1：新增测试没有证明申报的 W5 并发/重启/幂等矩阵

所谓“双客户端并发”实际先 await A 成功，再调用 B，不存在并发竞争（[`schedule-w5-concurrency-projection.spec.ts:171`](../../packages/schedule/src/server/application/services/__tests__/schedule-w5-concurrency-projection.spec.ts:171)）。worker “重启”只是复用同一个 in-memory repo 新建/调用同一 worker；“重复消费”只是第二次扫描已 completed 队列得到 0，并未把同一 message 再投递（[`schedule-w5-concurrency-projection.spec.ts:251`](../../packages/schedule/src/server/application/services/__tests__/schedule-w5-concurrency-projection.spec.ts:251)）。内存 transaction snapshot 和 outbox 状态机复制了期望语义，没有穿过 Prisma/PowerSync production adapter。

`schedule:test:integration` 当前唯一文件是 ScheduleTask repository 的两项持久化/identity 测试，与 CalendarEntry OCC、outbox、lease 和 conflict projection 无关（[`schedule-task-prisma.repository.integration.test.ts:54`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-task-prisma.repository.integration.test.ts:54)）。因此 329+2 全绿不能作为 W5 验证结论。

关闭条件：至少补真实 PostgreSQL 两连接/两事务 CAS 竞争、真实 PowerSync CAS/rollback、Prisma delete/update/outbox 回滚、worker crash/restart、同 message 重投、乱序 source revision、cache/base query 对比；并断言一个成功、一个结构化 conflict、最终 revision 与投影精确一致。

### 第二轮终审结论

**W5 第二轮仍不可放行：不要提交 W5，不进入 W6。**

本轮确实完成了两项重要主体修复：`expectedVersion` 已进入 update/delete 的公共 schema、HTTP/OpenAPI、IPC、client port 与 repository CAS，冲突错误也稳定携带 `context.currentVersion`；PowerSync repository 已有 affected-row CAS、`writeTransaction` fail-fast 和持久化 rebuild outbox 的实现骨架。app-vue fixture 的 required `version` 类型回归也已关闭。

但原 P1-3、P1-4、P1-5 仍未关闭：生产组合根没有给新 worker 注入持久化 lease coordinator，outbox claim/ack 不校验 claim token；一次多字段命令仍会让内存 aggregate revision 与数据库 revision/outbox source revision 分叉，worker 也完全不消费 outbox 的 `sourceRevision`；delete domain event 没有写入同事务 durable event outbox，而是在 commit 后直接向进程 event bus 发布。新增测试又没有覆盖这些失败窗口，且治理门禁实际失败。因此不能以“7 个 integration tests 全绿”替代语义关闭。

第二轮最终分级：**P0 = 0，P1 = 3，P2 = 2。**

### 已关闭：原 P1-1 的服务端与传输主体链路

### P1-1（原 P1-3）：worker 已接生命周期，但生产 lease、claim 与 ack 仍不安全

`ScheduleRebuildWorkerRuntime` 已作为 module-owned contribution 启停，这是有效进展（[`schedule.module.ts:276`](../../packages/schedule/src/server/infrastructure/schedule.module.ts:276)、[`schedule-rebuild-worker-service.ts:97`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:97)）。但 `createScheduleModule()` 在未注入时回退到 `new ScheduleLeaseCoordinator(null)`，Prisma 与 PowerSync 两个 production composition root 都没有传 `leaseCoordinator`（[`schedule.module.ts:280`](../../packages/schedule/src/server/infrastructure/schedule.module.ts:280)、[`prisma.ts:29`](../../packages/schedule/src/server/infrastructure/prisma.ts:29)、[`powersync.ts:41`](../../packages/schedule/src/server/infrastructure/powersync.ts:41)）。多进程 API/desktop 实际因此无分布式 lease，所谓每批 lease guard 在生产退化为永远成功。

更关键的是 claim 不是原子 ownership 转移。Prisma 先 select candidates，再按 id 无条件 `updateMany`，随后按 id 返回记录；没有在 update 条件和返回查询中限定旧状态或本次 `claimToken`（[`schedule-prisma.repository.ts:240`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:240)）。PowerSync 是同样的 select-then-update 结构（[`schedule-powersync.repository.ts:370`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:370)）。两边 `markRebuildOutboxProcessed(id, claimToken, ...)` 虽接收 token，SQL/Prisma where 却都只使用 id；超时后由新 worker 重新 claim 的记录仍可被旧 worker ack/retry/failed 覆盖（[`schedule-prisma.repository.ts:278`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:278)、[`schedule-powersync.repository.ts:418`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:418)）。

此外，worker 在 `ensureHeld()` 抛 lease-lost 后进入普通 catch，并在没有再次确认 lease ownership 的情况下写 retry/failed（[`schedule-rebuild-worker-service.ts:53`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:53)）。这不满足 claim token、lease guard 和崩溃恢复的关闭条件。

关闭条件：production roots 必须注入持久化 lease repository/coordinator；claim 必须是带 eligible-state 条件的原子抢占并只返回本 token 所有记录；ack/retry/failed 必须以 `id + claimToken + processing` 条件更新并检查 affected row；lease-lost 不得由失主继续改状态；补超时重领后旧 worker ack 的竞争测试。

### P1-2（原 P1-4）：投影列隔离已完成，但 revision-aware 语义仍错误

专用 `updateConflictProjection()` 现在只写 `hasConflict/conflictingSchedules`，不会再整聚合 save；相同值预检查也避免了普通重复应用写入。这一部分方向正确（[`schedule-prisma.repository.ts:157`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:157)、[`schedule-powersync.repository.ts:250`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:250)）。

但第一轮指出的 command revision 分叉没有修复。每个 aggregate mutation 仍各自 `version += 1`，例如 title、description 与 reschedule 会分别推进 revision（[`calendar-entry.ts:292`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:292)、[`calendar-entry.ts:318`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:318)、[`calendar-entry.ts:332`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:332)）；application service 可在一次 update command 中连续调用这些 mutation（[`schedule-event-application-service.ts:123`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:123)），而 Prisma/PowerSync CAS 都固定落库为 `expectedVersion + 1`（[`schedule-prisma.repository.ts:49`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:49)、[`schedule-powersync.repository.ts:91`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:91)）。随后 outbox 却记录内存 `schedule.version`（[`schedule-event-application-service.ts:144`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:144)）。多字段命令会再次产生 DB version=2、outbox sourceRevision=3/4/... 的分叉，使本应 stale 的投影更新被 `version <= sourceRevision` 放行。

worker 本身也没有读取或比较 `item.sourceRevision`；它只使用时间窗口重新查询，cache service 再把每个当前 schedule 自身的 `schedule.version` 当作 source revision（[`schedule-rebuild-worker-service.ts:53`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:53)、[`schedule-conflict-cache-service.ts:24`](../../packages/schedule/src/server/application/services/schedule-conflict-cache-service.ts:24)）。因此新增的 direct repository stale test 只证明一个局部 SQL 条件，不证明乱序 outbox、worker/client 并发或 revision-aware 消费。

关闭条件：一次业务命令只推进一个 canonical revision，并让 aggregate、DB 返回值、domain event 与 outbox source revision 完全一致；worker 必须显式处理 outbox `sourceRevision`；补多字段 update、旧/新 outbox 乱序、同消息重投和 worker/client 并发的真实 DB 断言。

### P1-1：Prisma 主路径改善，但 PowerSync claim/ack 仍不具备 token ownership

Prisma 的 claim 已把 `pending`、到期 `retry` 与超时 `processing` 统一为 `eligibleCondition`，条件同时用于候选查询和 `updateMany`，回读也限制为本次 `claimToken + processing`；成功 ack 使用 `id + claimToken + processing` 并在零行时抛错（[`schedule-prisma.repository.ts:267`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:267)、[`schedule-prisma.repository.ts:293`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:293)、[`schedule-prisma.repository.ts:305`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:305)、[`schedule-prisma.repository.ts:319`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:319)）。Requirement 6 也真实穿过 PostgreSQL，证明超时重领后旧 Prisma token 的成功 ack 被拒且记录仍归新 token（[`schedule-w5-real-concurrency.integration.test.ts:394`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:394)）。Prisma/PowerSync production root 现在都默认装配持久化 lease repository，这一部分关闭。

PowerSync 路径仍是 blocker。UPDATE SQL 中 `id IN (...)` 的占位符位于两个 eligible-time 占位符之前，但参数却按 `claimToken, now, now, threshold, threshold, ...ids` 传入；实际 id 位置收到 threshold，而尾部 id 又会落到状态时间条件，真实 SQLite 上不能按候选 id 完成 claim（[`schedule-powersync.repository.ts:387`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:387)）。即使 claim 成功，PowerSync success/retry/failed 三条 UPDATE 都只使用 `WHERE id = ?`，未使用传入的 `claimToken`、未要求 `status = 'processing'`、也未检查 `rowsAffected`；旧 worker 可以在超时重领后把新 owner 的记录 completed/retry/failed（[`schedule-powersync.repository.ts:422`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:422)）。Requirement 6 只实例化 `SchedulePrismaRepository`，完全没有覆盖 PowerSync ownership。

Prisma 的失败路径也未完整达到第二轮关闭条件：retry/failed 的 `updateMany` 已有 token/status 条件，但结果被丢弃，claim 丢失时静默 no-op（[`schedule-prisma.repository.ts:335`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:335)）。此外成功 ack 抛出的文本是 `no longer owned ... (lease lost)`，worker 只识别 `ScheduleLeaseLostError` 或包含 `lease ownership was lost` 的消息，因此该错误会落入普通失败处理，而不是直接中止本批（[`schedule-prisma.repository.ts:329`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:329)、[`schedule-rebuild-worker-service.ts:73`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:73)）。虽然第二次 token-guarded failure update 不会覆盖新 owner，但 lease-lost 语义和可观测结果仍不正确。

关闭条件：修正 PowerSync SQL 参数顺序；两 adapter 的 ack/retry/failed 一律使用 `id + claimToken + processing`、检查 affected row 并返回统一的 typed lease-lost；worker 对该错误直接退出且不再写状态；用真实 SQLite/PowerSync database 覆盖双 worker claim、超时重领、旧 token success/retry/failed 全矩阵。

### 已关闭：P1-2 canonical revision 与 source-revision CAS 主体

`CalendarEntry.update()` 现在先汇总字段变化，最后只执行一次 `version += 1`；多字段 update 不再产生内存 aggregate revision 与数据库 revision 分叉，delete 也明确推进一次 revision（[`calendar-entry.ts:292`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:292)、[`calendar-entry.ts:361`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:361)、[`calendar-entry.ts:282`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:282)）。application service 在 save/delete 后用命令后的 `schedule.version` 写 rebuild outbox，worker 显式把 `item.sourceRevision` 传给 cache refresh（[`schedule-event-application-service.ts:133`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:133)、[`schedule-event-application-service.ts:144`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:144)、[`schedule-event-application-service.ts:190`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:190)、[`schedule-rebuild-worker-service.ts:57`](../../packages/schedule/src/server/application/services/schedule-rebuild-worker-service.ts:57)）。Prisma/PowerSync 投影 UPDATE 都使用 `current.version <= sourceRevision` CAS，不会覆盖更新后的业务 revision。

因此 P1-2 实现主体可关闭。乱序、重投与 worker/client 并发的证据完整性仍计入 P2-1，不再把已修复的 command revision 问题保留为 P1。

### P1-3：新增表和事务写入不等于 durable event outbox

Prisma repository 现在会在 save/delete 同一个 transaction-scoped repository 中把 aggregate events 写入 `schedule_domain_event_outbox`，application service 也只在 transaction callback 成功后执行进程 event bus publish；真实 PostgreSQL 的 aggregate/rebuild-outbox 回滚已得到部分证明（[`schedule-prisma.repository.ts:50`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:50)、[`schedule-prisma.repository.ts:176`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:176)、[`schedule-event-application-service.ts:172`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:172)、[`schedule-event-application-service.ts:210`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:210)）。

但该表只有 `id/identityId/scheduleId/eventType/payload/createdAt`，没有状态、attempt、next-attempt、claim token、publishedAt 或 event idempotency key；仓库内也没有读取/claim/publish/ack 该表的 publisher。commit 后、application 直接 publish 前崩溃，或 publish 失败，记录虽然留在表中却永远不会被投递；直接 publish 成功后也不会把 outbox 标成已完成，未来无法安全重放（[`schedule.prisma:154`](../../packages/database/prisma/schema/schedule.prisma:154)）。这只是 durable event journal 的写入端，不是 durable delivery outbox。

PowerSync repository 的 save/deleteAggregate 则完全没有 domain-event outbox 写入（[`schedule-powersync.repository.ts:56`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:56)、[`schedule-powersync.repository.ts:224`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:224)）。本次实跑 `memoflow:governance-check` 仍被 `unflushed-events-audit` 拒绝，明确命中 `PowerSyncScheduleRepository.save()`，与“governance 通过、两个 repo 已满足审计”的申报相反。

回滚测试的外部事件断言也仍监听错误的 `'ScheduleEventDeletedEvent'`，实际 event type 是 `'schedule:calendar-entry-deleted'`；所以该 spy 不能证明 rollback 时零外部事件（[`schedule-w5-real-concurrency.integration.test.ts:245`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:245)、[`calendar-entry.ts:286`](../../packages/schedule/src/server/domain/aggregates/calendar-entry.ts:286)）。

关闭条件：为所有可启动 adapter 提供同事务 canonical event-outbox 写入；实现有 claim/retry/idempotency/ack 的可靠 publisher 与生产生命周期；覆盖 commit 后 publish 前崩溃、publish failure 重试、重复投递和正确 event type 的 rollback 零可见事件；governance 必须实跑通过。

### 已关闭：Requirement 3 的真实 SQLite CAS/回滚主体

Requirement 3 现在通过 `better-sqlite3(':memory:')` 创建真实 `schedules` 表，并把 `writeTransaction` 映射为 SQLite 的 `BEGIN/COMMIT/ROLLBACK`（[`schedule-w5-real-concurrency.integration.test.ts:18`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:18)、[`schedule-w5-real-concurrency.integration.test.ts:72`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:72)）。测试真实穿过 `PowerSyncScheduleRepository`，证明 revision 1 更新为 2、stale revision 返回结构化 conflict，并在 rebuild outbox 故障注入后恢复 title/version 2（[`schedule-w5-real-concurrency.integration.test.ts:359`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:359)）。第三轮关于 `Map` 模拟器不能证明 CAS/rollback 的这一部分关闭。

### P1-1：PowerSync claim 参数与 token ownership 仍未修复

第三轮指出的参数顺序错误原样存在。claim UPDATE 的前三个参数用于 SET，随后 SQL 先出现 `id IN (...)`，最后才是 retry/processing 的两个时间条件；实现却传入 `[claimToken, nowIso, nowIso, thresholdIso, thresholdIso, ...ids]`，因此 id 占位符收到时间，尾部 id 又进入时间条件（[`schedule-powersync.repository.ts:398`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:398)）。真实 SQLite Requirement 3 没有调用 `claimRebuildOutboxItems()`，所以 8/8 全绿没有覆盖该错误。

`markRebuildOutboxProcessed()` 也仍只按 `id` 读取和更新；success、retry、failed 都没有 `claim_token = ? AND status = 'processing'`，没有检查 `rowsAffected`，传入的 `claimToken` 实际未使用（[`schedule-powersync.repository.ts:433`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:433)）。超时重领后，旧 worker 仍可覆盖新 owner 的状态。Requirement 6 仍只覆盖 Prisma adapter（[`schedule-w5-real-concurrency.integration.test.ts:473`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:473)）。这是并发正确性 blocker，P1 保持打开。

### P1-2：governance 机械通过，但 domain event durable delivery 仍不存在

`memoflow:governance-check --skip-nx-cache` 本轮实跑成功，`unflushed-events-audit` 的确报告 97/17/0；因此“命令是否真实通过”答案是通过。但该审计只要 repository **文件任意位置**出现 `publishAggregateEvents` 等标识符，就把文件内所有相关 save 视为已 flush（[`unflushed-events.mjs:28`](../../tools/governance/lib/unflushed-events.mjs:28)、[`unflushed-events.mjs:77`](../../tools/governance/lib/unflushed-events.mjs:77)）。它不验证调用是否可达、是否发生在 commit 后、是否具备 outbox fallback 或能否重启重放。

当前 PowerSync production root 构造 repository 时没有注入 event bus（[`powersync.ts:29`](../../packages/schedule/src/server/infrastructure/powersync.ts:29)），而 `withTransaction()` 创建 transaction-scoped repository 时也没有传递 root 的 event bus（[`schedule-powersync.repository.ts:477`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:477)）。因此 application service 的正常 create/update/delete 路径仍由 `pendingEvents` 在 transaction 成功返回后统一 publish（[`schedule-event-application-service.ts:70`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:70)、[`schedule-event-application-service.ts:75`](../../packages/schedule/src/server/application/services/schedule-event-application-service.ts:75)）；production 路径当前不会双发。即使手工注入 event bus，PowerSync CAS update 分支也会在 repository publish 之前直接 `return`（[`schedule-powersync.repository.ts:71`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:71)、[`schedule-powersync.repository.ts:127`](../../packages/schedule/src/server/infrastructure/adapters/powersync/schedule-powersync.repository.ts:127)），可见新增代码并不是完整的 repository-owned flush 语义。

Prisma transaction repository 若被注入 event bus，则会继承该 bus 并在事务 callback 内 publish；`publishAggregateEvents` 随后清空 aggregate buffer，所以 application 的 post-transaction 循环不会再次发布，不会形成“双发”，但外部事件会在 commit 前可见（[`schedule-prisma.repository.ts:109`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:109)、[`schedule-prisma.repository.ts:366`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-prisma.repository.ts:366)、[`aggregate-repository.base.ts:119`](../../packages/patterns/src/repository/aggregate-repository.base.ts:119)）。这仍是错误的事务边界。

更关键的是，Prisma `ScheduleDomainEventOutbox` 仍只有 id、identity、schedule、type、payload、createdAt，没有 delivery status、attempt、nextAttemptAt、claim token、publishedAt 或 idempotency key（[`schedule.prisma:154`](../../packages/database/prisma/schema/schedule.prisma:154)）；Schedule 代码中仍没有读取、claim、publish、ack 该表的 publisher。PowerSync repository 则完全不写 domain-event outbox。application 的 post-commit direct publish 又没有传 `outboxWriter`；event bus 失败时 helper 只记日志并清空事件（[`aggregate-repository.base.ts:79`](../../packages/patterns/src/repository/aggregate-repository.base.ts:79)、[`aggregate-repository.base.ts:109`](../../packages/patterns/src/repository/aggregate-repository.base.ts:109)）。commit 后、publish 前崩溃或 publish 失败仍会永久丢失对外事件。第三轮 P1-3 因而保持为本轮 P1-2。

### P2-1：真实连接证据改善，但 worker crash/replay 矩阵仍不成立

Requirement 1 与 3 已关闭对应证据缺口；Requirement 4 仍只是声明一个从未调用的 `worker1`，在任何 claim/projection/ack 状态发生前把注释称为“crash”，随后由 `worker2` 第一次处理队列（[`schedule-w5-real-concurrency.integration.test.ts:409`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:409)）。它没有证明 claimed 后、projection 写后、ack 前崩溃的持久恢复，也没有同 message 重投、乱序 source revision、retry/backoff/max-attempt 或 PowerSync 双 worker ownership。Requirement 2 的“零外部 delete event”仍监听错误字符串 `'ScheduleEventDeletedEvent'`，而不是 domain aggregate 实际发出的 `schedule:calendar-entry-deleted`（[`schedule-w5-real-concurrency.integration.test.ts:324`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:324)）。这些仍是验证矩阵缺口，P2 保持打开。

### P1-2 保持打开：publisher 局部 at-least-once 正确，生产消费边界仍不成立

`IDomainEvent` 已新增 optional `idempotencyKey`，publisher 的 `publishEvent()` 从稳定 outbox row 复制该 key；process loop 无 `publishedAt` skip，publish 成功后再 ack（[`domain-event.interface.ts:13`](../../packages/contracts/src/shared/domain-event.interface.ts:13)、[`schedule-domain-event-publisher.ts:70`](../../packages/schedule/src/server/application/services/schedule-domain-event-publisher.ts:70)、[`schedule-domain-event-publisher.ts:116`](../../packages/schedule/src/server/application/services/schedule-domain-event-publisher.ts:116)）。单测将 row 恢复成 `pending + publishedAt null` 后重新处理，断言 bus 共收到两次、key 相等、最终 completed（[`schedule-domain-event-publisher.spec.ts:194`](../../packages/schedule/src/server/application/services/__tests__/schedule-domain-event-publisher.spec.ts:194)）。所以“publisher 不再用 publishedAt 掩盖 ack 丢失”和“publisher 内部构造稳定 key”可确认。

### P1-1 保持打开：metadata 已贯通，但可靠消费确认与原子副作用仍不存在

生产链路的 envelope 传递已确认，不再保留第六轮“实际消费者拿不到 key”的判断。`IEventSender.send()` 的第三参数是 optional，既有两参数 sender 在类型上仍兼容；Schedule production composition root 也继续通过统一 `createEventBusAdapter(eventBus)` 接入 publisher。相关 utils、patterns、Schedule、app-vue、API、desktop typecheck 本轮直接执行均通过，未发现这项签名扩展导致编译破坏。

问题在交付确认语义，而非 metadata 类型。`CrossPlatformEventBus` 的 ADR 契约本来就是通知式、发布方不等待订阅方；新增第二参数没有改变这一点。`ScheduleDomainEventPublisherService.publishEvent()` await 的只是 adapter 立即完成的 Promise，而不是 consumer receipt/side effect 的 transaction。随后 `markDomainEventOutboxProcessed()` 可以先于异步 consumer 完成。若进程在这两者之间退出，或 handler 的 Prisma 写失败，outbox 已 completed 且错误不会返回 publisher，事件会永久丢失。用测试侧 `setTimeout(50)` 只能让断言稳定，不能成为生产 acknowledgement。

测试消费者也没有原子事务。`findUnique -> create receipt -> sideEffects += 1` 是三个分离动作，其中 `sideEffects` 是 JavaScript 局部变量。unique constraint 只保证最多一条 receipt，不保证“receipt + 业务副作用”同 commit；它无法证明 receipt 已写但副作用前崩溃、或副作用完成但 receipt 写失败时能够收敛。并且 receipt key 未包含 consumer identity；若该通用表被多个副作用消费者共享，同一 envelope 的第一个消费者会阻止其他消费者各自记录回执。

关闭条件：不要把 fire-and-forget notification bus 当成可靠消费确认边界。publisher 必须 await 一个能够确认 durable handoff/consumer transaction 的 delivery adapter，确认后才 ack；或者先把事件原子投递到每个消费者自己的 durable inbox/二级 outbox。至少实现一个 production consumer，以 `(consumer, idempotencyKey)` 唯一键在真实 `$transaction` 中同时提交 receipt 与可查询的持久业务副作用，并把 duplicate-key 视为幂等成功；覆盖 handler/transaction 失败时 publisher 不 ack 或 durable handoff 可重放。

### P1-1 保持打开：drain 后置了 ack，但没有建立成功确认语义

生产接线本身成立：event sender 的 `awaitDrain?` 保持可选兼容，adapter 在 publish/send 后调用它，Schedule module 的默认 publisher 使用该 adapter。对一个正常 resolve 的 async handler，`processOutbox()` 现在会先等待 consumer transaction，再执行 `markDomainEventOutboxProcessed()`；第七轮指出的纯时间竞态在 success path 已关闭。

可靠交付需要的却是“成功才 ack”，而不是“无论成功失败都等到结束再 ack”。当前 `tracked` Promise 的 catch 只写日志且不重新抛出，`awaitDrain()` 无法看到 rejection；同步异常更是在 `invokeHandler()` 内直接吞掉。若 Requirement 10 的 Prisma transaction 因数据库中断、约束错误或业务写失败而 reject，publisher 得到的仍是 resolved `eventBus.publish()`，随后把 outbox completed，事件不能再由 durable outbox 重投。这与代码注释声称的 at-least-once 交付边界相冲突，也没有任何测试覆盖“真实 bus handler reject -> publisher retry/failed、outbox 不 completed”。

receipt/effect 用例也只在 integration test 中注册临时 consumer；仓库内 `ScheduleEventConsumerReceipt` 的唯一读写方仍是 Requirement 10。把 `effectCount` 放在 receipt 自身的 create 中，只证明一行插入原子，不证明 receipt 与一个可查询、具有业务含义的独立持久副作用同 commit。并发 duplicate-key loser 未被识别为幂等成功，恰好会触发上述异常吞噬路径。因此第七轮 P1 不能关闭。

关闭条件：可靠 publisher 使用的 delivery seam 必须把至少一个 consumer 的失败反馈给 `publish()`，使 outbox 进入 retry/failed 而非 completed，同时仍允许通知式 bus 保持原有隔离语义；实现一个 production consumer，在同一真实事务中写 consumer-specific receipt 与独立持久业务副作用，显式把并发 unique conflict 视为幂等成功；补真实 bus 的 success、sync throw、async reject、transaction rollback 与并发 duplicate-key 测试，逐项断言 outbox 状态和数据库副作用。

### P2-1 保持打开：Requirement 10 仍不是真实 crash/restart/concurrency 证据

本轮确实新建了第二个 `ScheduleDomainEventPublisherService`，并改用数据库 receipt/effectCount 断言；这两点相对第七轮有进展。但第一次 `publisher.processOutbox()` 已经正常 publish 并 ack completed，测试随后通过直接 `updateMany` 把行改回 `pending`。这不是 publish 返回后、ack 写入前的确定性 fault point，也没有留下并老化真实 `processing + claimToken` 状态（[`schedule-w5-real-concurrency.integration.test.ts:609`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:609)、[`schedule-w5-real-concurrency.integration.test.ts:619`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:619)）。

所谓重启只替换 publisher；repository、全局 bus、adapter、已注册 consumer、`seenKeys` 与 Prisma client 全部复用。测试注释所称“process restart”与实际实例边界不符。两次 delivery 又是串行执行，没有并发首次投递，不能证明 `findUnique -> create` 的 unique-conflict loser 会幂等成功。数据库最终 receipt count/effectCount 为 1 是有效的串行去重证据，但不足以关闭第七轮要求的真实 fault/restart/concurrent atomic 矩阵。

关闭条件：在 `publishEvent()` 成功与 outbox ack 之间加入确定性 fault injection；丢弃 publisher、bus、adapter、consumer、repository/client 等进程内对象，仅保留数据库状态，老化真实 claim 后用全新组合重启；再用两个并发 delivery 覆盖首次 duplicate-key 竞争，并只以 outbox、consumer receipt 和独立业务副作用数据库状态判定收敛。

### P1-1 保持打开：R13 证明唯一约束获胜者，但没有可靠的 production 幂等消费

R13 的并发本身是真实的：两个 `createEventBusAdapter(eventBus)` 并发发布同 key，handler 内使用真实 `prisma.$transaction()`，最终唯一约束保证最多一条 receipt。该测试关闭了“是否真实并发触碰数据库唯一约束”这一狭窄证据缺口。

它没有关闭第八轮 P1。consumer 先 `findUnique`，不存在时再 `create`；并发首次 delivery 可以都读到不存在，loser 的 `create` 抛 Prisma unique violation。consumer 没有捕获该错误并在确认 winner 已提交后返回幂等成功（[`schedule-w5-real-concurrency.integration.test.ts:734`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:734)）。`CrossPlatformEventBus` 又在 async handler 的 `.catch()` 中只记录错误并把 tracked Promise 转成 fulfilled，`awaitDrain()` 使用 `Promise.allSettled()` 且不检查 rejection；同步 throw 同样只记录日志（[`cross-platform-event-bus.ts:40`](../../packages/utils/src/domain/cross-platform-event-bus.ts:40)、[`cross-platform-event-bus.ts:80`](../../packages/utils/src/domain/cross-platform-event-bus.ts:80)）。所以两个 `adapter.publish()` 都可 resolve，publisher 仍可 ack completed；R13 的 `Promise.allSettled` 也没有断言 delivery 结果，测试绿灯掩盖了 loser 失败。

原子副作用仍未实现。schema 只有 `ScheduleEventConsumerReceipt`，`effectCount` 就在 receipt 同一行；测试所谓 side effect 只是创建 receipt 时给该字段赋 1，并没有写一个独立、可查询且有业务含义的持久 projection/effect 表（[`schedule.prisma:175`](../../packages/database/prisma/schema/schedule.prisma:175)）。仓库内 `scheduleEventConsumerReceipt` 的运行时读写也只出现在 W5 integration test，没有 production consumer 被 module/runtime 装配。`effectWins` 是未断言的进程内计数器，且 `schedule:lint` 也把它报告为 unused（[`schedule-w5-real-concurrency.integration.test.ts:733`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:733)）。

生产 publisher 的接线路径仍成立：Schedule module 默认以 `createEventBusAdapter(eventBus)` 创建 publisher，adapter 在 sender 支持时调用 `awaitDrain()`（[`schedule.module.ts:287`](../../packages/schedule/src/server/infrastructure/schedule.module.ts:287)、[`events/index.ts:112`](../../packages/patterns/src/events/index.ts:112)）。但这只证明“等待 handler 结束”，没有证明“handler 成功才 ack”。因此第八轮 P1-1 保持打开。
