## P1-1：Knowledge ledger/replay 只到 HTTP client，没有形成 UI 与 desktop 可用闭环

服务端 list/replay 实现本身存在（[`knowledge-repository-projection.service.ts:544`](../../packages/repository/src/server/application/services/knowledge-repository-projection.service.ts:544)、[`knowledge-repository-projection.service.ts:598`](../../packages/repository/src/server/application/services/knowledge-repository-projection.service.ts:598)），HTTP adapter 也暴露了对应方法。但全仓搜索表明 app-vue 没有任何 `listKnowledgeWriteRequests`、`replayKnowledgeWriteRequestProjection` 或 `projectionStatus` 的消费点；因此用户无法看到 `Committed + Pending/Failed`，也无法触发 replay 或刷新状态。

Desktop transport 更不是“forward”：IPC adapter 的两个新增方法都直接返回 `serverProjectionUnavailable()`（[`repository-ipc.adapter.ts:170`](../../packages/repository/src/infrastructure-client/adapters/ipc/repository-ipc.adapter.ts:170)）。所谓双 transport surface test 只断言源码包含方法名（[`knowledge-write-request-ledger-contract.surface.spec.ts:53`](../../packages/repository/src/application-client/knowledge-write-request-ledger-contract.surface.spec.ts:53)），没有断言 IPC 行为，更无法证明 UI/服务端一致。

关闭条件：在实际 Knowledge 页面接入 list、状态刷新和 Pending/Failed replay，显示 commit 与 projection 两条状态及可操作错误；为 web 与 desktop 明确可用 transport（或明确 desktop 统一走 HTTP），补组件/页面行为测试，证明失败、刷新、重放成功后的 UI 与服务端 ledger 一致。

## P1-2：Settings defaults 没有生产初始化，分类 reset 参数被静默丢弃

`loadDefaults()` 现在能调用 service 并写 store（[`useUserSetting.ts:69`](../../packages/app-vue/src/modules/setting/composables/useUserSetting.ts:69)），但它只在新增单测里被调用；生产代码没有任何调用点。`UserSettingsView` 只解构并调用 `loadSettings`，presentation bootstrap 也只请求 `getUserSettings()`（[`UserSettingsView.vue:58`](../../packages/app-vue/src/modules/setting/views/UserSettingsView.vue:58)、[`usePresentationBootstrap.ts:60`](../../packages/app-vue/src/modules/setting/composables/usePresentationBootstrap.ts:60)）。所以新 getter 的 defaults fallback 在真实启动中仍通常是 `null`。

同时 `resetToDefaults(_category)` 明确忽略参数，并始终调用无参 `service.resetUserSettings()`（[`useUserSetting.ts:99`](../../packages/app-vue/src/modules/setting/composables/useUserSetting.ts:99)）。分类 reset 会意外重置全部分类。新增 app-vue 测试只覆盖手工 `loadDefaults()` 和 store fallback，没有覆盖 reset 后 UI，也没有捕获丢参。

真实 DB 的无记录 reset 两项测试通过，证明 server use case 能 materialize 默认 aggregate；这个局部通过不能替代客户端初始化与分类命令链路。

关闭条件：在唯一启动/设置 bootstrap 中初始化 defaults，并定义与 `loadSettings` 的失败及并发顺序；传递 category 到 client；补页面级测试证明新用户启动可见默认值、分类 reset 不改其他分类、全量 reset 后 UI 与返回 aggregate 一致。

## P1-3：认证 receipt 能恢复到 store，但没有恢复到用户界面

store 初始化会从 localStorage 读取 receipt（[`authentication-store.ts:38`](../../packages/app-vue/src/modules/authentication/stores/authentication-store.ts:38)），成功 mutation 会清除（[`usePassword.ts:52`](../../packages/app-vue/src/modules/authentication/composables/usePassword.ts:52)）。然而 app-vue 中 `passwordMutationError` 除 store 实现和测试外没有任何消费点，`usePassword()` 本身也没有生产调用点。刷新后 receipt 虽在内存中，用户页面仍不会显示 message、request id、retryability 或 retry action，因而不满足“页面卸载/刷新恢复可操作错误”的体验目标。

关闭条件：在真实密码修改/忘记密码/重置密码页面使用 `usePassword`，渲染恢复后的结构化错误与 request id，并按 `retryable` 提供动作；补真实组件卸载、重新挂载/应用 bootstrap 测试，而不只是新建 Pinia 后直接读取 store。

## P1-4：“错误不泄露凭据”没有由实现或测试保证

receipt builder 保存传入的 `message`。该 message 来自 `translateResultError`；当没有翻译 key 时，公共 translator 会回退为原始 `ResultError.message`（[`result-error.ts:175`](../../packages/http-client/src/result-error.ts:175)）。因此如果上游错误消息包含 reset token、当前/新密码、邮箱参数或其他敏感输入，它会被原样写进持久 localStorage（[`authentication-store.ts:57`](../../packages/app-vue/src/modules/authentication/stores/authentication-store.ts:57)）。

现有“不泄露”测试给出的错误消息只是 `Current password is incorrect`，再断言 receipt 不含请求中的两个 secret（[`usePassword.spec.ts:187`](../../packages/app-vue/src/modules/authentication/composables/usePassword.spec.ts:187)）；实现从未接触该 request 对象，这个断言天然会通过。测试没有把 secret/token 放进 `error.message` 或 context，也没有检查持久化字符串。

关闭条件：持久 receipt 只保存 code、经过 allowlist 的本地化安全文案、request id、operation、retryability、timestamp；不得保存任意 server message/context。测试必须注入包含 password/token/email 的恶意/回显错误，断言 store 与 localStorage 均不含敏感值。

## P2-1：四项 Knowledge 集成测试不是所描述的 webhook 故障矩阵

“webhook delay”测试直接依次调用 repository 的 `markCommitted`、`bindProjectionSource`；“webhook failure”直接调用 `markProjectionFailed`，没有发送 webhook，也没有让 `applyChanges` 抛错（[`knowledge-write-request-projection-ledger.integration.test.ts:76`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:76)、[`knowledge-write-request-projection-ledger.integration.test.ts:101`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:101)）。“external Git refresh”也直接调用 repository 的 `markProjectionSucceededByCommit`，没有经过 reconcile/webhook service（[`knowledge-write-request-projection-ledger.integration.test.ts:214`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:214)）。

## P2-2：预存 `setup.ts` localStorage 补丁在当前 Node 下没有真正安装，并缺少测试隔离

补丁只在 `typeof globalThis.localStorage === 'undefined'` 时创建 happy-dom Storage（[`setup.ts:8`](../../packages/app-vue/src/test/setup.ts:8)）。当前 Node 暴露了 `globalThis.localStorage`，但未配置 `--localstorage-file`；全量 app-vue 测试的每个 worker 都报告 `ExperimentalWarning: localStorage is not available because --localstorage-file was not provided`。因此 guard 判断为“已存在”，实际却不可用。认证新测试之所以通过，是该 spec 自己无条件覆盖了 global localStorage，而不是公共 setup 生效。

此外公共 hooks 不会在每项测试前清空 storage；一旦公共 setup 真正安装共享 Storage，同一 worker 内测试可能互相污染。当前 874/874 绿不能证明该补丁正确，只证明现有顺序没有触发失败。

关闭条件：公共 setup 应安装经功能探测可读写的 Storage，并在测试间清理或明确按 suite 隔离；删除 spec 内的重复全局覆盖后，认证 reload 测试与全量 app-vue 仍应无 localStorage warning 通过。

## P2-1：已关闭——迟到 Failed 真正到达 ledger guard，非 lease `CONFLICT`

可控屏障位于 B 的 connection lookup：B 已在 `replayWriteRequestProjection` 中读取到同一记录的 `Pending` 快照并越过 `Succeeded` early return，但尚未获取 lease（[`knowledge-write-request-projection-ledger.integration.test.ts:977`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:977)）。此时 A 从同一非终态记录启动，经真实 service replay 完成 projection 写入和 `markProjectionSucceeded`，返回 `Succeeded`（[`knowledge-write-request-projection-ledger.integration.test.ts:987`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:987)）。

A 完成并释放 lease 后，测试才为 B 设置一次真实 `applyChanges` 异常并释放 connection barrier。B 随后取得空闲 lease、使用先前读取的 Pending 快照进入 `replayWriteRequestCore`；`applyChanges` 抛错后，service 的 catch 在有效 lease 下调用真实 `markProjectionFailed`（[`knowledge-repository-projection.service.ts:715`](../../packages/repository/src/server/application/services/knowledge-repository-projection.service.ts:715)）。B 的断言结果是 `SERVICE_UNAVAILABLE`，而不是未取得 lease 时的 `CONFLICT`（[`knowledge-write-request-projection-ledger.integration.test.ts:996`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:996)）。结合该 catch 路径无其他返回分支，这证明迟到失败写实际到达 ledger transition。

真实 Prisma `markProjectionFailed` 使用 `where: { id, identityId, projectionStatus: { not: 'Succeeded' } }`；A 已落下 `Succeeded` 后，B 的 updateMany 更新 0 行，终态 guard 拒绝倒退（[`knowledge-write-request-prisma.repository.ts:125`](../../packages/repository/src/server/infrastructure/adapters/prisma/knowledge-write-request-prisma.repository.ts:125)）。该 repository 返回值虽未由 service 向外透传，但最终数据库状态和 attempts 断言能够区分“guard 拒绝”与“Failed 曾落库”。
