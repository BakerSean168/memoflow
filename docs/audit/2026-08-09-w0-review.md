# W0 实施结果审查

## 结论

**结论：W0 暂不能进入 W1/W2。**

交付物目录、ADR、审计报告和 contracts 子路径均已新增，且未发现业务模块代码被修改；但核心契约尚未达到计划要求的“版本化、状态语义自洽、可关联回执、可安全 claim”标准。审计报告还把已经存在的 Task 事务 runner 记为不存在。以下 P1 问题修复并补齐负向测试前，不应开始依赖这些契约的 W1/W2 迁移。

## P1：应该在进入 W1/W2 前修复

### 1. “版本化”契约没有版本字段

计划要求版本化 `BusinessOperationReceipt`（计划第 52 行），ADR 也把它描述为标准契约（ADR-042 第 36-50 行），但 [operation-receipt.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:80) 的 `BusinessOperationReceiptSchema` 没有 `schemaVersion`/`contractVersion`。`OutboxMessage` 已有独立的 `schemaVersion`，但不能替代回执版本（[reliable-messaging.prisma](/workspace/repos/memoflow/packages/database/prisma/schema/reliable-messaging.prisma:9)）。

**建议：**在 `BusinessOperationReceipt`、`DeliveryAttempt`、`LeaseClaim`、`ProjectionOperation` 约定明确的正整数版本字段和演进策略，并在正/负向测试中锁定未知版本行为；ADR-042 第 119-120 行同步说明。

### 2. Zod schema 没有校验时间格式和状态字段不变量

`expiresAt`、`attemptedAt`、`nextRetryAt`、`deadLetterAt`、`createdAt` 等均是裸 `z.string()`（[lease.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/lease.ts:7)、[operation-receipt.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:35)、[operation-receipt.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:80)），`ProjectionOperation.sourceRevision` 还允许任意字符串、任意数字（[projection.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/projection.ts:8)）。因此 `not-a-date`、`NaN`、负 revision 都可通过。

更重要的是，schema 允许相互矛盾的回执：`running` 可以没有 lease，`retryable` 可以没有 `nextRetryAt`/`lastError`，`dead_letter` 可以没有 `deadLetterAt`，终态可以没有 `finishedAt`，并且成功结果可以携带错误。ADR-042 第 56-65 行已经规定了这些状态的语义，但实现没有 `superRefine` 或按状态 discriminated schema 执行这些约束。

**建议：**使用 `z.iso.datetime()`（或仓库统一的时间 schema）和有限的 revision schema；用 `superRefine`/discriminated union 明确 lease、错误、重试时间、死信时间和完成时间的必备关系，并增加每种非法组合的测试。

### 3. 合成幂等字符串存在分隔符碰撞，且 schema 不验证其一致性

`buildIdempotencyKeyString` 直接拼接 `identityId:source:occurrenceKey`（[operation-receipt.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:56)、[operation-receipt.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:70)）。字段本身允许 `:`，例如 `(a:b,c,d)` 与 `(a,b,c:d)` 产生相同字符串。`BusinessOperationReceiptSchema` 也只检查 `idempotencyKey` 非空（[operation-receipt.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:80)），可接受与三个组成字段不匹配的 key。

**建议：**采用不可歧义的编码（长度前缀、结构化 canonical encoding 或禁止/转义分隔符），并在 schema/refinement 中由 `identityId/source/occurrenceKey` 校验 key 与组成字段一致；补碰撞负向测试。

### 4. `ProjectionOperation` 没有闭环到 BusinessOperationReceipt

计划要求每个 operation 能关联 receipt、`lastError`、`nextRetryAt` 和 dead-letter（计划第 54 行）。但 [projection.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/projection.ts:8) 只有 projector、revision、status、replayable、cursor 和 lastError，没有 `operationId`、identity/correlation/causation、attempt、lease、nextRetryAt 或 deadLetterAt。ADR-042 第 72-79 行同样只列了这组不完整字段。

**建议：**让投影操作持有 `operationId`/幂等键并复用 receipt（嵌入或明确引用），定义 projection 与 receipt 的状态映射、重放和授权查询契约；同步修正 ADR 和审计报告第 137 行的“已冻结”表述。

### 5. `LeaseClaim` 缺少资源标识和 fencing 代数

`LeaseClaim` 只有 owner、expiry、heartbeat 和 interval（[lease.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/lease.ts:7)）。没有 lease/resource key、唯一 claim id 或单调 fencing token。租约过期后旧 worker 仍可能凭旧 ownerToken 写入，无法实现计划风险表要求的 fencing（计划第 125 行）和 W1 的 conditional claim（计划第 60 行）。

**建议：**增加受保护资源键、claim/lease id 和数据库生成的单调 fencing token，并在 ADR-042 第 67-70 行定义 stale-owner 拒绝规则。

### 6. capability fail-fast 函数忽略契约自身的必需性字段

`CapabilityRequirementContractSchema` 暴露了 `requiredInProduction` 和 `allowTestDoubleInTest`（[capability.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/capability.ts:22)），但 `assertProductionCapabilityOrFailFast` 只按环境和 status 判断（[capability.ts](/workspace/repos/memoflow/packages/contracts/src/modules/reliable-messaging/capability.ts:56)），完全不读取 `requiredInProduction`；`allowTestDoubleInTest` 也未被任何校验使用。这使 contract 的声明与执行语义不一致。

**建议：**明确 optional capability 的 production 行为，按 `requiredInProduction` 决定是否抛错，并在 test 环境校验 `test_double` 是否被显式允许；增加 required/optional、test-double allowed/denied 四类测试。

### 7. 基础设施盘点与当前代码事实不一致

审计报告称 Task “无独立 `TaskTransactionRunner` 抽象”（[w0-infrastructure-audit.md](/workspace/repos/memoflow/docs/audit/2026-08-09-w0-infrastructure-audit.md:98)）并称模板/实例/outbox 缺乏强制事务（第 102-104 行）。当前代码已有 `TaskWriteTransactionRunner`、Prisma 实现和 `$transaction`（[task-write-support.ts](/workspace/repos/memoflow/packages/task/src/server/application/use-cases/commands/task-write-support.ts:12)、[prisma-task-write-transaction-runner.ts](/workspace/repos/memoflow/packages/task/src/server/infrastructure/adapters/prisma/prisma-task-write-transaction-runner.ts:15)、[prisma.ts](/workspace/repos/memoflow/packages/task/src/server/infrastructure/prisma.ts:35)）。不过 use case 仍保留可选参数并可回退到 inline runner（[create-task-template.use-case.ts](/workspace/repos/memoflow/packages/task/src/server/application/use-cases/commands/create-task-template.use-case.ts:35)），所以真实缺口是“应用层允许 fallback/非强制”，不是“没有 runner”。

**建议：**按当前实现重写审计结论，区分已有 adapter 与组合根强制性；为 W4 指向可选注入和 `createInlineTaskWriteTransactionRunner` 的确切删除/拒绝启动边界。

### 8. W0 要求的各模块 application port 没有交付

计划 W0 的涉及文件明确包含“各模块 `application` port”（计划第 50 行），但变更文件只有 reliable-messaging contracts、ADR、审计报告、索引和计划链接；没有任何 Reminder/Notification/Account/Goal/Task/Schedule/Repository application port 或迁移边界接口。W1/W2 因而只能直接自行定义适配接口，无法保证共用 W0 receipt。

**建议：**至少冻结各模块依赖的 operation/delivery/lease/projection port（接口和错误/授权边界即可，不实现业务行为），并在计划中列出实际文件；否则将 W0 交付范围收窄并明确这是未完成项。

### 新问题

#### P1-1：Projection 状态不变量与 receipt 不一致

`ProjectionOperationSchema` 复制了大部分 receipt refinement，但没有实现 ADR-042 对 `pending` 的 `lease=null/deadLetterAt=null` 约束，也没有对 `dead_letter`、`retryable` 之外状态清理 `nextRetryAt`/`deadLetterAt` 的规则。于是同一 projection 可被 schema 接受为带 lease 的 `pending`，再通过 `projectionOperationToReceipt` 变成违反统一状态词典的 receipt。应抽取共享状态 refinement 或直接由同一 schema 映射，补齐每个状态的正反向约束。

#### P1-2：Application port 没有形成可验证的 receipt 输入闭环

`NotificationOutboxDispatchInputSchema` 和 `AccountClosureSagaInputSchema` 接收任意非空 `idempotencyKey`，却没有 `source/occurrenceKey`，无法验证它是否为 canonical `identity + source + occurrence` key；`GoalReliableOperationPort`、`TaskReliableOperationPort` 等接口同样只传部分标识。ports 虽然已交付名称和方法，但不能阻止适配器生成与 `BusinessOperationReceipt` 不一致的回执。W0 至少应统一 port 输入中的幂等三元组，或定义专用、可校验的 operation input schema，并明确输出必须经 receipt schema parse。

#### P2-1：幂等键 parser 接受不合法的空字段和宽松长度

`parseIdempotencyKeyString` 使用 `parseInt` 且允许长度为 0；例如 `v1:0::0::1:x` 会解析出空 `identityId/source`，而 `7x` 之类前缀也可能被当成数字。该函数不是 `buildIdempotencyKeyString` 的严格逆运算。应使用全数字长度 token、要求三字段非空，并以 `BusinessOperationIdempotencyKeySchema` 对解析结果做最终校验；补 malformed/empty/round-trip 负向测试。

#### P2-2：Projection `sourceRevision` 与 ADR 的“有效 SHA/UUID”要求不一致

实现只限制字符串非空并排除字面量 `NaN`，任意 `"garbage"` 都能通过；ADR-042 明确要求有效 Git commit SHA/UUID。应收窄字符串格式，或把 ADR 约束改为“opaque non-empty revision”并说明由适配器验证。

#### P2-3：统一状态词典与遗留 Outbox 状态并存

`reliable-messaging/index.ts` 仍公开独立的 `OutboxMessageStatus = pending/dispatched/failed/dead`，与 ADR-042 声称的 8 状态不一致。若这是兼容的 R1 legacy 类型，应在 ADR/索引中明确其边界和映射；否则后续模块可能继续绕过 `BusinessOperationStatus`。

#### P2-4：fencing 校验的 `nowIso` 未经格式校验

`validateLeaseFencing` 直接对调用方传入的 `nowIso` 做 `new Date(...).getTime()`；非法值产生 `NaN`，比较结果为 false，可能错误放行。应先用 `IsoDatetimeSchema` 校验或在无效时间时返回拒绝。

### 边界与工作树核对

- 未发现 Reminder、Notification、Account、Goal、Task、Schedule、Repository/Knowledge 等业务模块实现被本轮工作树改动；变更仅限 contracts reliable-messaging、ADR/审计/计划文档及 ADR 索引。
- 未发现 W0 新增隐式 fallback/no-op 成功路径。现有 Notification runtime 的 no-op 和 Task inline runner 仍存在，但 W0 只盘点并冻结边界，不能据此宣称 W1/W2 已 fail-closed。
- capability 函数是纯契约校验，尚未接入生产组合根；因此“有 fail-fast schema”不等于“生产启动已 fail-fast”。

### 第二次最终判定

**结论：W0 仍不能进入 W1/W2。** 第一轮 8 项已全部得到代码或文档层面的对应交付，其中状态不变量和幂等性仍有上述残余；新增的 P1-1（Projection 状态闭环）和 P1-2（application port/receipt 闭环）属于后续迁移的基础契约缺口，必须先修复。P2 项应在同一轮补齐 parser、revision、legacy 状态映射和 fencing 时间输入测试。修复后重新运行 contracts test/typecheck/lint/governance-check，并对业务模块零改动与组合根 fail-fast 接入做专门核验，之后才可重新判断 W1/W2 放行。

### 新问题

#### P2-5：嵌套契约未执行未知 schemaVersion 拒绝

`BusinessOperationReceiptSchema` 与 `ProjectionOperationSchema` 会拒绝大于当前版本的值，但 `LeaseClaimSchema`、`DeliveryAttemptSchema` 和 `CapabilityRequirementContractSchema` 只有正整数校验，没有同等的“不得高于 `RELIABLE_MESSAGING_SCHEMA_VERSION`” refinement（`lease.ts:12-29`、`operation-receipt.ts:45-65`、`capability.ts:24-39`）。因此回执内可嵌入未来版本 lease/attempt，能力契约也可接受本实现未知版本，和第一轮“版本字段锁定”的验收语义不一致。应统一版本 schema/refinement，并补 nested future-version 负向测试。

### 回归、边界与事实核对

- 前两轮已修复的 receipt/projection 版本字段、fencing resource/claim/token、capability required/optional 与 test-double fail-fast、幂等键碰撞防护、审计事实修正和 application ports 文件交付均仍存在，未发现本轮回退。
- 未发现 Reminder、Notification、Account、Goal、Task、Schedule、Repository/Knowledge 等业务模块实现被本轮工作树修改；未发现本轮新增隐式 fallback/no-op 成功路径。现有 Notification no-op 与 Task inline runner 仍是后续迁移边界，不能作为 W0 已 fail-closed 的证据。
- capability fail-fast 仍只是 contracts 层纯校验，尚未证明已接入生产组合根；因此不能把“函数存在”升级为“生产启动一定失败”。

### 第三次终审判定
