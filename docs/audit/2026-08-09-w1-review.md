# W1 审查：Reminder 调度与投递意图重构

审查范围为 `docs/plan/active/2026-08-09-business-p0-elegant-fix-plan.md` 的 W1 小节、W0 reliable-messaging 契约，以及工作区中未提交的 W1 产物。未修改业务代码、未提交或推送。

## 结论

**W1 不可放行，不能进入 W2/W3。** 当前实现对“真实 cron + durable occurrence + 单事务写入”有部分实现，但没有满足 W0 的 fail-closed 和完整 receipt/lease 状态机不变量。

## Findings

### P0-1：运行时仍存在可达的空 runtime/no-op

`createReminderRuntimeContribution()` 在没有 `cronContribution` 时返回空的 `start/stop`（[reminder.runtime.ts:49-57](../../packages/reminder/src/server/infrastructure/runtime/reminder.runtime.ts:49)）。同时默认 `isEnabled` 为 true（[reminder.runtime.ts:32-35](../../packages/reminder/src/server/infrastructure/runtime/reminder.runtime.ts:32)），因此生产代码直接调用该工厂不会 fail-fast，而会宣称 capability available 后静默不调度。W0/计划明确禁止 implicit fallback/no-op success；这使 Reminder P0 仍可在错误组合下完全不执行。

### P0-2：调度器保留旧的进程内触发 fallback

`ReminderSchedulerService` 的可靠依赖是可选参数（[reminder-scheduler-service.ts:72-81](../../packages/reminder/src/server/domain/services/reminder-scheduler-service.ts:72)）；任一依赖缺失就走 `triggerService.triggerRemindersBatch()`（[reminder-scheduler-service.ts:220-229](../../packages/reminder/src/server/domain/services/reminder-scheduler-service.ts:220)）。该路径分步保存聚合/历史，绕过 occurrence、lease 和事务 outbox，正是 W1 要删除的根因路径。组合根当前传入依赖不能抵消这个可达 API/构造路径。

### P1-1：lease 只有过期抢占，没有 heartbeat/续租操作

数据库保存 `lastHeartbeatAt` 与 `heartbeatIntervalMs`（[reminder.prisma:191-196](../../packages/database/prisma/schema/reminder.prisma:191)），但 `ReminderReliableOperationPort` 只定义 `claimOccurrence` 和 `recordDeliveryIntent`（[ports.ts:85-94](../../packages/contracts/src/modules/reliable-messaging/ports.ts:85)），适配器也没有 heartbeat 方法。长事务超过 30 秒会被第二实例抢占；旧 owner 只在最终事务开始时检查 fencing（[prisma-reminder-write-transaction-runner.ts:49-83](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:49)），没有运行中续租闭环，不能满足 owner/expiry/heartbeat 的计划语义。

### P1-2：失败、重试和死信没有状态机落库

事务 runner 只产生 `succeeded` 或 `skipped`（[prisma-reminder-write-transaction-runner.ts:85-93](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:85)），异常在调度器中仅转换成返回值并调用 `recordFailed()`（[reminder-scheduler-service.ts:205-213](../../packages/reminder/src/server/domain/services/reminder-scheduler-service.ts:205)）。没有写入 `retryable`、`nextRetryAt`、`dead_letter` 或 `deadLetterAt`；metrics 的 `recordRetry/recordDeadLetter` 仅有未被调用的计数器（[reminder-metrics-service.ts:38-44](../../packages/reminder/src/server/domain/services/reminder-metrics-service.ts:38)）。因此 W0 要求的可重试、死信和可观测指标不成立。

### P1-3：Notification intent 没有数据库级幂等约束

runner 每次创建 outbox 时生成随机消息 ID（[prisma-reminder-write-transaction-runner.ts:140-158](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:140)），幂等键只嵌在 `payloadJson`；`OutboxMessage` 没有 `idempotencyKey` 列或唯一索引（[reliable-messaging.prisma:9-27](../../packages/database/prisma/schema/reliable-messaging.prisma:9)）。W0 要求的是 durable、可查询且唯一的 delivery intent。当前无法由数据库阻止相同 notification intent 的重复插入，也无法按键进行条件 upsert。

### P1-4：暂停/分组禁用不会生成 durable skipped occurrence

`getPendingReminders()` 在 claim 前过滤掉未启用模板（[reminder-trigger-service.ts:183-209](../../packages/reminder/src/server/domain/services/reminder-trigger-service.ts:183)）。因此调度器不会为暂停、全局禁用或分组禁用写 occurrence/history；runner 的 `isEnabled=false` 分支（[prisma-reminder-write-transaction-runner.ts:89-93](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:89)）只有被直接调用才可达。测试声称的 disabled skip 没有覆盖真实 cron 调度路径，且过期/时区边界同样没有调度级证据。

## W0/schema 对照

`ReminderOccurrence` 已包含 `templateId + occurrenceKey` 唯一约束、canonical `idempotencyKey`、owner/expiry/fencing/attempt/重试字段（[reminder.prisma:182-214](../../packages/database/prisma/schema/reminder.prisma:182)），其 receipt 映射也调用 schema 校验（[reminder-reliable-operation-prisma.adapter.ts:20-66](../../packages/reminder/src/server/infrastructure/adapters/prisma/reminder-reliable-operation-prisma.adapter.ts:20)）。但 Prisma 状态字段为自由字符串，且上述 heartbeat、retry/dead-letter 字段没有实际状态转换。新增 `Account.reminderOccurrences` 关系与 occurrence 的 identity 外键在数据库层合理，但它不能代替业务 identity-scoped 查询；当前关系还未证明是 W1 必需而非仅为 ORM 导航。

## 测试质量

文件名与实施说明声称 7 个用例，但实际只有 5 个（[reminder-reliable-operation.integration.test.ts:45-314](../../packages/reminder/src/server/infrastructure/adapters/prisma/__tests__/reminder-reliable-operation.integration.test.ts:45)）。双实例测试使用 `Promise.all` 发起两个 claim，能覆盖基本竞争；崩溃测试通过 100ms lease + 150ms sleep 模拟过期（[reminder-reliable-operation.integration.test.ts:125-155](../../packages/reminder/src/server/infrastructure/adapters/prisma/__tests__/reminder-reliable-operation.integration.test.ts:125)），但没有在写历史、推进 next trigger、写 outbox 各个点注入崩溃，也没有断言回滚后不重复。没有 heartbeat、retry/dead-letter、暂停/分组、过期、时区、真实 cron 生命周期或 outbox 幂等断言。

本地验证受环境阻断：`pnpm` 不在当前 shell 中，无法运行 Nx integration/typecheck/lint targets。

## 分级与放行决定

- **P0**：P0-1 空 runtime/no-op；P0-2 旧 fallback 仍可达。
- **P1**：P1-1 heartbeat/续租缺失；P1-2 retry/dead-letter 未落库；P1-3 outbox 缺少唯一幂等约束；P1-4 disabled/paused 调度路径未形成 durable receipt；测试覆盖不足。
- **P2**：生成 Prisma 文件产生大量与业务无关的 diff/格式噪声（`git diff --check` 报告 generated `index.d.ts` 多处 trailing whitespace），增加审查和回滚风险，但不是放行阻断的根因。

在 P0/P1 问题修复并补齐真实并发、故障注入、状态机和边界测试前，W1 不应宣称完成，也不应进入后续工作包。

### 新问题与回归

**P1-5：retryable/dead_letter 没有遵守重试与死信语义。** `recordOccurrenceFailure()` 写入 `retryable` 的 `nextRetryAt`，但 `claimOccurrence()` 的 existing 分支只判断终态和 lease 是否过期；对无 lease 的 `retryable` 或 `dead_letter`，`isLeaseExpired` 为真，会立即重新 claim（[reminder-reliable-operation-prisma.adapter.ts:144-186](../../packages/reminder/src/server/infrastructure/adapters/prisma/reminder-reliable-operation-prisma.adapter.ts:144)）。scheduler/trigger 查询也没有按 `nextRetryAt` 或 dead-letter 状态拦截。由于失败发生在事务 runner 外，模板的 `nextTriggerAt` 未推进，真实 cron 下一分钟可重复领取死信，且不会等待退避或人工 replay。W0 将 `dead_letter` 定义为等待运维 replay 的非终态；当前行为违反该契约。**此为放行阻断的 P1。**

**P1-6：cron stop 不是 graceful drain。** `stop()` 只停止 node-cron task 并清空句柄，不等待已进入 `execute()` 的 Promise；`ReminderModule.dispose()` 随后即可返回，而正在运行的 scheduler 仍可能写入 occurrence/history/outbox（[reminder-trigger-cron-job.ts:87-123,140-146](../../packages/reminder/src/server/infrastructure/cron/reminder-trigger-cron-job.ts:87)）。W1 完成定义要求 start/stop/dispose 生命周期和 graceful shutdown 可观察，当前没有 in-flight drain 或停止标志。**P1。**

**P2-1：组合根 API 留有绕过强制依赖的注入口。** `createReminderTriggerCronJob()` 允许传入可选 `schedulerService`，此时跳过 `reliablePort`/`transactionRunner` 检查（[reminder-trigger-cron-job.ts:37-82](../../packages/reminder/src/server/infrastructure/cron/reminder-trigger-cron-job.ts:37)）。当前生产组合根没有使用该口，且 scheduler 构造本身已强制依赖，但该公开工厂仍可被错误 adapter/test double 接线，形成契约边界不一致。**P2（若该入口进入生产 wiring 则升级 P1）。**

### 测试真实性与边界

- 所谓“12 个集成测试”当前文件实际只有 10 个 `it()`（编号 1--10）。用例 1 的 `Promise.all` 确实并发发起两个 adapter claim，但没有并发执行 scheduler 的完整事务写入；用例 2 只是等待 100ms lease 过期后重新 claim，并未在 history、next trigger 或 outbox 各写入点做故障注入和回滚不重复断言。
- 用例 6 直接调用 adapter heartbeat，证明续租 API 的 DB 行为，不证明长事务期间存在自动续租闭环。用例 7 通过复制 receipt 手工把 `attempt` 改为 3，验证的是写入映射，不是 cron 重试调度、退避或死信 replay；也没有暴露上述 P1-5。
- 用例 9 已经走 `ReminderSchedulerService.schedule()`，因此 paused/group-disabled 的 skipped 声明有真实扫描路径证据。用例 10 的断言（Tokyo 09:00 对应 UTC 00:00）在该固定日期/非 DST 时区下合理，但只覆盖一个时区点，未覆盖 DST 或日期边界；没有 cron start/stop/dispose 生命周期测试。
- outbox 唯一约束用例直接操作 Prisma `create`，能证明数据库约束，但没有证明 runner 在并发重复事务下以幂等方式处理唯一冲突并返回原 receipt。

### 分级与放行结论

- **P0：无新增。** 第一轮 P0-1、P0-2 已按生产/开发 fail-fast 与强制构造路径修复。
- **P1：P1-5 retry/dead-letter 领取语义；P1-6 cron graceful drain；heartbeat 自动续租仍未闭环；failed 终态缺少真实落库路径；测试声明数量与覆盖范围不符。**
- **P2：P2-1 可选 schedulerService 绕过 capability 检查；P2-2 测试与文档将 10 个用例称为 12 个、时区/故障注入覆盖偏窄。**

**结论：W1 仍不可放行，不能进入 W2/W3。** 只有修复 retry/dead-letter 的 claim/replay/退避不变量、补齐运行中 heartbeat 与 graceful drain，并用真实 cron/并发/故障注入测试证明后，才可重新评估放行。

### 回归与边界

- 第一轮两个 P0 无回退：production/development 缺失 cron capability 继续 fail-fast；scheduler 的可靠依赖仍为强制依赖，旧 `triggerRemindersBatch()` fallback 不在 `schedule()` 路径中。
- 失败会持久化 `retryable/dead_letter` 并记录 failed/retry/dead-letter metrics；但所有执行异常都只进入 retryable，达到次数后进入 dead-letter，仍没有契约中不可重试终态 `failed` 的分类和落库路径。加上上述 stale-owner 无条件 failure write，状态机不能视为完整关闭。
- outbox 的 `idempotencyKey @unique` 和同事务写入仍在；durable `skipped` 仍由真实 scheduler scan、control check 和 transaction runner 形成，未见回退。

### Account timezone port 依赖方向与失败行为

- **依赖方向本身合理，无循环依赖。** `AccountTimezonePort` 由 Reminder domain 拥有，application 依赖抽象，adapter 位于 Reminder infrastructure；adapter 只消费一个结构化 account application surface，没有从 Reminder domain/application 反向 import Account infrastructure/ORM。当前 governance 的 package-internal boundary 为 641 files / 0 violations，未形成 `reminder ↔ account` 项目循环。
- **P1：账号读取失败被两层静默吞掉并伪装成“账号未配置”。** adapter 捕获 `getProfile()` 异常后返回 `null`，application 又捕获 port 异常后返回 UTC，均无日志、metric、结构化错误或 retryability；adapter 注释甚至写“异常时不吞吐错误”，行为与注释相反（[account-timezone-adapter.ts:17](../../packages/reminder/src/server/infrastructure/adapters/account-timezone-adapter.ts:17)、[reminder-schedule-query-application-service.ts:38](../../packages/reminder/src/server/application/services/reminder-schedule-query-application-service.ts:38)）。账号不存在/未配置可以按契约进入显式 UTC，但依赖超时、数据库错误或 account API 失败不应被无观测地视为同一状态，否则 Today window 可成功返回错误日期。至少应在 port result 中区分 absent 与 unavailable，并选定 fail-fast 或有日志/指标的明确降级策略。
- **P2：当前 port 仍是可选 capability，且出现未使用的 domain scheduler 参数。** query service、module dependencies 都把账号 port 声明为 optional；`ReminderSchedulerService` 也新增同名可选构造参数却从未读取。真正接线前应收敛到唯一 composition seam，避免“可选即默认 UTC”的第二条生产路径与无效依赖。
