## P1-1：`@memoflow/contracts/operations` 是无法运行时导入的声明 export

`packages/contracts/package.json` 将 `./operations` 指向 `dist/modules/operations/index.js`（[`package.json:32`](../../packages/contracts/package.json:32)），但 contracts 的 tsup entry 没有 `src/modules/operations/index.ts`（[`tsup.config.ts:18`](../../packages/contracts/tsup.config.ts:18)）。本轮实际执行 `contracts:build` 后，目录中只有 `.d.ts/.map`，没有 `index.js`；随后执行：

```text
node --input-type=module -e "import('@memoflow/contracts/operations')..."
ERR_MODULE_NOT_FOUND .../packages/contracts/dist/modules/operations/index.js
```

源码 path alias 使 typecheck 与 Vitest 都能通过，不能证明发布子路径可用。W7 新增的五模块代码大量运行时 import 该子路径中的 Zod schema，因此这是发布阻断，不是单纯打包整洁度问题。

关闭条件：把 operations 加入 contracts 的真实 JS/DTS 构建入口；清空/重建产物后用 package export 做 ESM smoke import，并为每个新 export 增加产物存在性门禁。

## P1-2：治理门禁实测失败，与“governance 通过”申报冲突

`nx run memoflow:governance-check` 本轮退出码为 1。失败来自 Package Export Audit：

```text
packages/contracts/package.json exports "./operations" which is not in the allowed whitelist
packages/patterns/package.json exports "./operations" which is not in the allowed whitelist
```

其余已运行治理子检查通过，但总门禁失败就不能记为“governance 通过”。这也说明新增公共 surface 没有完成治理同步。

关闭条件：按 canonical 公共 surface 规则登记两个 export，并复跑完整 `memoflow:governance-check` 到退出码 0；不得只引用其中先打印的局部 `[governance-check] passed`。

## P1-3：五个 timeline 查询均未写 `timeline_query` 审计

审计 contract 明确定义 `replay | timeline_query`（[`audit-record.ts:4`](../../packages/contracts/src/modules/operations/audit-record.ts:4)），schema 注释和 ADR 也宣称 query/replay 都必须审计。但全仓 `timeline_query` 只出现在 contract 与 ADR，没有任何生产记录调用。

例如 Reminder 查询只调用可靠端口后直接返回（[`reminder.module.ts:346`](../../packages/reminder/src/server/infrastructure/reminder.module.ts:346)），Notification 查询同样直接返回（[`notification.module.ts:274`](../../packages/notification/src/server/infrastructure/notification.module.ts:274)）；Knowledge、Schedule、Account 也是相同结构。现有集成测试只断言 replay audit，不断言 timeline query audit。

identity 数据隔离本身大体成立：查询 identity 来自认证 context，Prisma/ledger 查询也按 identity 过滤。但“最小权限 + 审计”只完成了前半段。

关闭条件：明确 query 审计粒度（每次请求记录 source、过滤条件、结果计数，避免把任意 operationId 伪造成被访问事实），五模块实现并测试 `timeline_query`；审计失败时采用一致、文档化的 fail-closed 策略。

## P1-4：Replay 状态变更与审计不原子，且 Knowledge 存在无审计成功路径

Reminder 先执行 `replayDeadLetter` 改状态，再 `auditRepository.record`（[`reminder.module.ts:356`](../../packages/reminder/src/server/infrastructure/reminder.module.ts:356)）；Notification（[`notification.module.ts:244`](../../packages/notification/src/server/infrastructure/notification.module.ts:244)）、Account（[`account.module.ts:167`](../../packages/account/src/server/infrastructure/account.module.ts:167)）、Schedule（[`schedule.module.ts:388`](../../packages/schedule/src/server/infrastructure/schedule.module.ts:388)）顺序相同。若第二步失败，API 虽返回错误，operation 已经进入 retryable/pending/running，留下 ADR 明令禁止的“发生 replay 但没有审计记录”。catch 不能回滚前一步。

Knowledge 更直接：它先执行真实 projection replay，只在 `result.ok && auditRepository` 时记录；没有 audit repository 时照样返回成功（[`repository.module.ts:156`](../../packages/repository/src/server/infrastructure/repository.module.ts:156)）。这与同文件 audit 查询的 `FAIL_CLOSED` 形成不一致，也违反“禁止 silent success/no-op fallback”。现有测试只覆盖数据库和审计都成功的 happy path，没有注入 audit write failure。

关闭条件：把 operation 状态推进与 audit 事实放进同一事务/同一原子应用端口；对无法共享事务的外部 projection 定义可靠 audit intent/outbox，再由可证明的状态机完成，不得靠“先执行、后写日志、失败返回错误”。五模块补 audit repository 故障注入测试，并让 Knowledge 缺依赖时 replay fail-closed。

## P1-5：统一指标只完成命名函数和两个进程内 collector，未形成五模块 dashboard 证据

共享 recorder 是进程内 `Map` + snapshot（[`unified-operation-metrics.ts:24`](../../packages/patterns/src/operations/unified-operation-metrics.ts:24)）。全仓真实 `recordOutbox/recordWorker` 调用只存在于 Reminder 与 Notification metrics service：

- Reminder 只记录 `claimed/failed/retried/dead_letter`，没有 `persisted/succeeded`。
- Notification 记录六个 outbox state。
- Knowledge、Schedule rebuild、Account closure 没有任何 recorder 调用。
- 五模块都没有真实 `recordWorker` 调用；`workerMetricKey` 只在 surface test 中出现。
- 没有 dashboard、Prometheus/OTel exporter 或其他生产消费点读取 unified snapshot。

新增 metrics spec 是直接手工调用 collector 后断言 key 名称；它证明命名函数正确，不证明 persisted/claimed/retried/failed 在真实工作流都发射，更不证明“五模块接入同一 dashboard”。

关闭条件：五个模块在真实 persistence/claim/retry/failure/dead-letter/worker outcome 路径接统一 recorder；接入现有 telemetry exporter/dashboard；用 worker/adapter 行为测试断言事件触发，而不是直接调用 metrics 方法。

## P1-6：跨模块门禁不是申报的五模块、W0--W6 故障注入矩阵，ADR/runbook 也未覆盖 W3--W6 关键决策

新增唯一跨模块 test 自己就说明只覆盖 Reminder、Notification、Schedule rebuild、Account closure 四模块（[`w7-cross-module-operation-gate.integration.test.ts:18`](../../packages/account/src/server/infrastructure/adapters/prisma/__tests__/w7-cross-module-operation-gate.integration.test.ts:18)）。实际聚合长度固定为 4，source 断言也只有四项（[`w7-cross-module-operation-gate.integration.test.ts:214`](../../packages/account/src/server/infrastructure/adapters/prisma/__tests__/w7-cross-module-operation-gate.integration.test.ts:214)）；Knowledge 没有进入同一门禁。

该测试只 seed 四条最终失败记录，验证 identity 拒绝、状态 reset 和共享 replay audit。它没有横切 W0--W6 的关键故障：事务提交/发布边界、lease fencing/丢 lease、渠道 capability/silent success、account closure 分阶段恢复、schedule expectedVersion/冲突与 rebuild 幂等、knowledge webhook/reconcile/乱序 replay 等。因此它是有效的 W7 四模块 happy recovery test，但不是申报的跨版本故障矩阵。

ADR-043 也把回归门禁写成“四模块”，并只描述 W7 overlay；runbook 只列端点和通用 replay。两者没有回收 W3--W6 的关键决策、判障信号、恢复步骤与禁止回退项，且文档中的“query/replay 都审计”“审计先行”“五模块指标”与代码不符。

关闭条件：建立可枚举的 W0--W6 故障矩阵（故障、注入层、预期 durable fact、恢复动作、禁止状态、测试文件），把 Knowledge 纳入同一跨模块 gate；ADR/runbook 引用并覆盖 W3--W6 的关键状态机、告警和恢复流程，内容必须与最终代码一致。

## P2-1：Desktop/PowerSync 宣称接入审计，但本地表与组合根未闭环

Electron audit adapter 直接读写 `reliable_operation_audit_logs`（[`electron-operation-audit-repository.ts:19`](../../packages/patterns/src/operations/electron-operation-audit-repository.ts:19)），但全仓没有对应 SQLite/PowerSync `CREATE TABLE` 或 schema 定义；只有 Prisma 模型。Notification 和 Schedule PowerSync 组合根却已经实例化该 adapter（[`notification/powersync.ts:367`](../../packages/notification/src/server/infrastructure/powersync.ts:367)、[`schedule/powersync.ts:56`](../../packages/schedule/src/server/infrastructure/powersync.ts:56)），实际调用 audit 会命中不存在的本地表。

同时 Reminder PowerSync 组合根没有注入 `reliablePort/auditRepository`（[`reminder/powersync.ts:63`](../../packages/reminder/src/server/infrastructure/powersync.ts:63)），Account PowerSync 也没有 closure operation repository/audit repository（[`account/powersync.ts:15`](../../packages/account/src/server/infrastructure/powersync.ts:15)），其 W7 API 会 fail-closed/抛错。当前 W7 integration 全是 Prisma lane，未覆盖这些组合根。

关闭条件：要么明确 W7 运维入口只属于 server lane并删除 Electron adapter/错误文档，要么补齐本地 schema、四/五模块组合根与真实 PowerSync 测试；不得维持“类型上可调用、运行时缺表/缺依赖”的半接入状态。

## P2-2：Prisma 生成声明使 diff hygiene 门禁失败

`git diff --check` 报告 `packages/database/src/generated/prisma/index.d.ts` 多处 trailing whitespace。文件虽为生成物，但当前在 W7 变更集内，提交前仍会造成常见 diff/patch 门禁失败和无效噪音。

关闭条件：使用仓库 canonical Prisma generate/format 流程产生稳定、无 trailing whitespace 的受管产物，并让 `git diff --check` 无输出。

## 终审结论

**W7 第三轮仍不可放行：不要提交 W7，W0--W7 尚未闭环。**

P1-3 与 P1-4 已关闭：五模块均有 query marker/filters/resultCount 证据和审计失败 fail-closed 测试；Knowledge replay 也已真正改成 audit intent 先落库，缺依赖或首次审计写失败时不会调用 projection，durable ledger 与 projection 均不变化。四个 Prisma replay 继续保持状态与审计同事务。

但 P1-5、P1-6 与 P2-1 未关闭。Reminder/Notification 的 retry 与 dead-letter 分支仍同时增加 `outbox.failed`，直接违反第二轮“retry/dead-letter 不笼统计为 failed”的关闭条件；Schedule 也仍没有 persistence 指标发射点。ADR-044 的 W7-2 行仍用 `packages/<module>/.../<file>` 形式的省略路径，并非真实精确文件引用。contracts/patterns 的 `test` target 仍不依赖自身 `build`；本轮移走两包 operations dist 后直接执行 test，两包 surface test 各有 2 项失败，clean checkout 门禁不自洽。

local Docker prod-like 未能完成。当前环境没有 `pnpm`，且缺 `.env.production.local`；额外执行等价的 `web:build` target 后复现了 `@memoflow/app-vue` 根 alias 把认证子路径解析成 `src/index.ts/modules/authentication` 的 production build 错误。该 import 与 alias 配置在 `HEAD` 中已原样存在，W7 没有修改对应文件，因此它是 pre-existing 阻断，不计为 W7 新增 finding；但按仓库发布规范，完整 prod-like 不能据此记为通过。

最终分级：**P0 = 0，P1 = 2，P2 = 1。**

## 指标生命周期专项结论

第三轮新增的行为测试不是全部停留在直接调用 collector：Schedule 使用真实 `ScheduleRebuildWorkerService` + Prisma repository（[`schedule-w5-real-concurrency.integration.test.ts:772`](../../packages/schedule/src/server/infrastructure/adapters/prisma/schedule-w5-real-concurrency.integration.test.ts:772)），Knowledge 驱动真实 projection service 与 Prisma ledger（[`knowledge-write-request-projection-ledger.integration.test.ts:1207`](../../packages/repository/src/server/infrastructure/adapters/prisma/__tests__/knowledge-write-request-projection-ledger.integration.test.ts:1207)），Account 驱动真实 coordinator（[`account-closure-coordinator.spec.ts:128`](../../packages/account/src/server/application/services/__tests__/account-closure-coordinator.spec.ts:128)），Reminder/Notification 也各有真实 scheduler/runtime 路径断言。这一方向有效。

问题在于行为测试把错误语义锁成了 green：Reminder 测试把 retry 与 dead-letter 都计入 failed；Notification 的真实 runtime 测试只断言 legacy `failedTotal/deadLetterTotal`，没有断言统一 retry/dead-letter key 与 failed key 互斥（[`notification.runtime.spec.ts:184`](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.spec.ts:184)）。因此“有行为测试”不能关闭“指标准确性”条件。

按当前代码实际存在的 lifecycle：

- Reminder：persisted → claimed → succeeded，失败分叉为 retryable 或 dead_letter，外加 worker completed/failed/skipped；retryable/dead_letter 不应再增加终态 failed。
- Notification：persisted → claimed → succeeded，失败分叉为 retryable 或 dead_letter，外加 worker completed/failed；同样不应双计 failed。
- Schedule rebuild：当前持久化 outbox → claimed → succeeded 或 retried/dead_letter，外加 worker completed/failed/skipped；缺 persisted 发射点。
- Account closure：persisted → running claim/reclaim → succeeded 或 failed；failed 再认领为 retried，worker completed/failed。当前没有实现独立 dead-letter 转移，不能为追求六个统一 key 而伪造不存在的 lifecycle。
- Knowledge：commit 持久化 → replay claim → succeeded/failed，Failed 再 replay 为 retried，worker completed/failed；当前没有独立 dead-letter 状态。
