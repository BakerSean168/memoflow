# W3 第一轮审查：AccountClosureCoordinator 骨架

本次审查对照 [`2026-08-09-business-p0-elegant-fix-plan.md`](../plan/archive/2026-08-09-business-p0-elegant-fix-plan.md) 的 W3、小节所列第一轮范围以及 W0--W2 审查标准，复核当前工作区未提交实现。审查只新增本文档；未修改业务代码，未 commit/push。

## 结论

**W3 第一轮不可放行，不能进入第二轮。**

当前产物具备 operation schema、Coordinator/port/repository 类型、顺序阶段推进、失败后按已保存 phase 重试、CloseAccountUseCase 委托以及 Cloud Auth 批量删除 session/device code 的局部骨架。account 168 个单测、2 个名为 integration 的用例、build/typecheck，以及 cloud-auth 16 个单测/typecheck 均通过。

但生产 API 与 Desktop 的 canonical account module factory 都没有注入 Coordinator 所需依赖，注册时会直接抛错；Cloud Auth 的批量撤销方法没有适配到 Account port。Coordinator 的仓储契约只有 find + 无条件 upsert，没有 owner/lease/version/条件阶段转换；并发执行会重复撤销、关户和发布事件，同一 idempotency key 还可跨 identity 返回他人的 receipt。`requested` 阶段并未实际阻断登录/refresh，cloud user/provider account 也未禁用或删除。account-closed 事件没有生产 publisher/outbox/consumer，Reminder、Notification、Repository pending work 不会因闭户取消。绿测未触达上述生产路径。

### 双视角判定

- **PM 视角**：用户点击注销后，当前 API/桌面模块可能在注册阶段不可用；即使绕过 wiring，用户仍可重新登录，关闭 receipt 也被 transport 丢弃，不能兑现“安全注销、明确退出、可查询进度”的产品承诺。
- **项目经理视角**：第一轮基础不变量尚未成立，第二轮若直接接 account-closed consumer，会建立在可重复发布、无 durable outbox、无生产 publisher 的不稳定接口上，扩大 W1/W2 pending work 误取消或漏取消风险。必须先关闭本轮 P0，再进入第二轮。

## 根因判定

根因不是缺少更多 `try/catch` 或测试数量，而是**把单进程内的顺序流程当成了可恢复 saga，却没有把并发所有权、条件状态转换、生产依赖装配和外部副作用幂等纳入持久化契约**：

1. operation repository 只暴露读取和整行保存（[`i-account-closure-operation-repository.ts:25`](../../packages/account/src/server/domain/repositories/i-account-closure-operation-repository.ts:25)），无法表达 `requested -> revoking`、owner claim、stale owner 拒绝或 publish completion CAS。
2. Prisma adapter 使用按 idempotency key 的无条件 `upsert`（[`account-closure-operation-prisma.repository.ts:45`](../../packages/account/src/server/infrastructure/adapters/prisma/account-closure-operation-prisma.repository.ts:45)），并发调用者可以互相覆盖并同时执行外部副作用。
3. Account、Cloud Auth、event publisher 分属不同 composition root，但没有一个生产根同时持有并装配它们；当前只在测试中手工拼装。
4. “闭户开始即阻断认证”和“闭户完成后取消异步投递”没有成为认证中间件/worker 的共享 durable policy，只存在注释或未接线 port。

因此这是架构与接线根因，不是局部实现遗漏。

## Findings

### P0-1：生产 composition root 未接线，API 与 Desktop account module 注册必然失败

`AccountModuleDependencies` 把 closure repository、revocation port、event publisher 和 coordinator 全部声明为可选（[`account.module.ts:17`](../../packages/account/src/server/infrastructure/account.module.ts:17)），`createAccountUseCases()` 在缺失这些依赖时抛错（[`account.module.ts:61`](../../packages/account/src/server/infrastructure/account.module.ts:61)、[`account.module.ts:75`](../../packages/account/src/server/infrastructure/account.module.ts:75)）。这能防止静默降级，但不是生产接线完成。

真实 API factory 仍只传 `accountRepository` 和 runtime contributions（[`prisma.ts:24`](../../packages/account/src/server/infrastructure/prisma.ts:24)、[`prisma.ts:30`](../../packages/account/src/server/infrastructure/prisma.ts:30)），`AccountApiModule.register()` 无额外依赖地调用它（[`module.ts:36`](../../packages/account/src/api/module.ts:36)、[`module.ts:39`](../../packages/account/src/api/module.ts:39)）。Desktop factory 同样只传 PowerSync account repository（[`powersync.ts:15`](../../packages/account/src/server/infrastructure/powersync.ts:15)、[`powersync.ts:21`](../../packages/account/src/server/infrastructure/powersync.ts:21)），Electron 注册直接调用该 factory（[`electron/index.ts:55`](../../packages/account/src/electron/index.ts:55)）。所以两个 canonical runtime 都会在创建 use cases 时抛出第 77 行错误。

全仓生产调用点只有 `createCloudAuth()` 返回的 `revokeAllSessions()`（[`cloud-auth.ts:44`](../../packages/cloud-auth/src/server/cloud-auth.ts:44)、[`cloud-auth.ts:176`](../../packages/cloud-auth/src/server/cloud-auth.ts:176)），没有将其包装为 `CloudAuthRevocationPort.revokeAll()` 并传给 account module，也没有 `AccountClosureEventPublisher` 的生产实现。当前只有测试手工构造这三个依赖。

**影响**：不是“关闭账号功能未启用”，而是 Account API/Desktop 模块整体无法注册，属于直接发布阻塞。

### P0-2：不是并发安全的可恢复 saga；幂等键也未绑定 identity

Coordinator 先按裸 idempotency key 查记录（[`account-closure-coordinator.ts:55`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:55)），若查到 succeeded/running 就直接返回该记录（[`account-closure-coordinator.ts:58`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:58)），从未校验 `existing.identityId === identityId`。数据库唯一约束也只是全局 `idempotencyKey @unique`（[`reliable-messaging.prisma:62`](../../packages/database/prisma/schema/reliable-messaging.prisma:62)）。不同 identity 使用同一 key 时，后者会收到前者包含 identityId/operationId 的 receipt，形成跨租户语义错误和信息泄露。

两个并发首次请求可同时 `find -> null`，随后都保存 running。Prisma `upsert` 的冲突方会更新同一行而不是失去执行权；两个调用者仍会继续调用 `revokeAll()`、`accountRepository.save()` 和 publisher。所有 phase 更新都是内存改字段后整行 save（[`account-closure-coordinator.ts:95`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:95) 至 [`account-closure-coordinator.ts:154`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:154)），没有 expected phase/status/version/owner 条件，也没有 lease expiry/heartbeat/fencing。

默认 key 由 identityId 和用户填写的 reason 拼接（[`close-account.use-case.ts:26`](../../packages/account/src/server/application/use-cases/commands/close-account.use-case.ts:26)），而公开 schema 根本不接受 idempotency key（[`account-lifecycle.dto.ts:3`](../../packages/contracts/src/modules/account/api/account-lifecycle.dto.ts:3)）。同一用户换一个注销原因就会创建第二个 operation；客户端重试也不能显式复用请求级 key。这不是严格的闭户幂等语义。

失败恢复虽能从 `revoking`/`closing` 继续，但有关键不确定窗口：外部撤销完成后、保存 `revoked` 前崩溃会重复撤销；account save 完成后、保存 `closed` 前崩溃会重读已关闭 account；publish 完成后、保存 succeeded receipt 前崩溃会重复发布。重复撤销本身可设计为幂等，但当前 publisher/downstream 没有稳定 event id/inbox 证明，整体仍不是可恢复 saga。

### P0-3：认证关闭生命周期未成立，`requested` 不阻断新登录/refresh，身份主体也未禁用

Coordinator 在 requested 阶段只把 phase 改为 revoking；“CloudAuth adapter checks closure operation state”只是注释（[`account-closure-coordinator.ts:95`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:95)），Cloud Auth options、hooks、session resolution 和 Better Auth route 中均没有 closure operation/account status guard（[`cloud-auth.ts:30`](../../packages/cloud-auth/src/server/cloud-auth.ts:30)、[`cloud-auth.ts:53`](../../packages/cloud-auth/src/server/cloud-auth.ts:53)、[`cloud-auth.ts:145`](../../packages/cloud-auth/src/server/cloud-auth.ts:145)）。认证路由在业务 auth middleware 之前直接挂载（[`bootstrap.ts:81`](../../apps/api/src/bootstrap.ts:81)、[`bootstrap.ts:102`](../../apps/api/src/bootstrap.ts:102)），所以 account status middleware 不能阻止 sign-in/refresh endpoint 自身创建新 session。

`revokeAllSessions()` 只删除 `cloudAuthSession` 和 `cloudAuthDeviceCode`（[`cloud-auth.ts:176`](../../packages/cloud-auth/src/server/cloud-auth.ts:176)）；没有禁用/删除 `cloudAuthUser` 或 `cloudAuthProviderAccount`，也没有 tombstone/denylist。用户凭据仍存在，可再次登录。`CloudAuthRevocationPort` 的名字和注释也只承诺 session（[`cloud-auth-revocation.port.ts:5`](../../packages/account/src/server/application/ports/cloud-auth-revocation.port.ts:5)），没有表达“撤销认证能力”与“删除用户数据/PII”的两个独立政策动作。

API 业务请求在 account 真正变为非 Active 后确实会被 middleware 拒绝（[`auth-middleware.ts:34`](../../apps/api/src/shared/infrastructure/http/middlewares/auth-middleware.ts:34) 至 [`auth-middleware.ts:41`](../../apps/api/src/shared/infrastructure/http/middlewares/auth-middleware.ts:41)），这是局部 fail-closed；但它发生在 closing 之后，不能覆盖 requested/revoking 窗口，也不能阻止认证端点重新发 session。当前会话客户端也没有明确 signed-out receipt/event 接线。

### P0-4：account-closed 没有 durable 生产发布与 consumer，异步读取/新投递未 fail-closed

Coordinator 依赖抽象 `AccountClosureEventPublisher`（[`account-closure-event-publisher.port.ts:11`](../../packages/account/src/server/application/ports/account-closure-event-publisher.port.ts:11)），但全仓没有生产实现或装配。与此同时，`Account.close()` 已产生 `account:closed` domain event（[`account.ts:164`](../../packages/account/src/server/domain/aggregates/account.ts:164)、[`account.ts:175`](../../packages/account/src/server/domain/aggregates/account.ts:175)），Prisma repository 保存后立即发布进程内 aggregate events（[`account-prisma.repository.ts:99`](../../packages/account/src/server/infrastructure/adapters/prisma/account-prisma.repository.ts:99)），Coordinator 又在 closed phase 调用另一 publisher（[`account-closure-coordinator.ts:134`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:134)）。若未来把该 port 直接接到同一 event bus，会双发；若进程在 publish 后、operation succeeded 保存前崩溃，重试还会再次发布。

全仓没有 Reminder、Notification、Repository 对 `account:closed` 的生产订阅/Inbox receipt，也没有 worker 在 claim/投递前查询 account/closure operation。当前这些模块只按自身 Active/pending 状态工作，已排队 reminder/notification/repository work 会继续执行。第二轮要求的 pending work 取消消费尚未实现，第一轮也没有提供可安全消费的 durable、唯一事件。

**影响**：闭户后 HTTP 业务访问的局部门禁不能替代后台 worker fail-closed；用户仍可能收到关闭后的通知或触发 repository work。

### P1-1：receipt 没有贯穿 transport，running 被当作成功且客户端看不到 operation

CloseAccountUseCase 对 `running` receipt 直接返回 `ok(receipt)`（[`close-account.use-case.ts:29`](../../packages/account/src/server/application/use-cases/commands/close-account.use-case.ts:29) 至 [`close-account.use-case.ts:40`](../../packages/account/src/server/application/use-cases/commands/close-account.use-case.ts:40)）。Controller 随后丢弃 receipt 并固定序列化 `data: null`（[`account.controller.ts:79`](../../packages/account/src/server/transport/account.controller.ts:79) 至 [`account.controller.ts:91`](../../packages/account/src/server/transport/account.controller.ts:91)），契约也仍定义 `CloseAccountRes = null`（[`account-lifecycle.dto.ts:9`](../../packages/contracts/src/modules/account/api/account-lifecycle.dto.ts:9)），client service 返回 `Result<void>`（[`account-client-service.ts:97`](../../packages/account/src/application-client/services/account-client-service.ts:97)）。

因此“running -> 进行中”和 retryable receipt 只存在服务端内部，客户端无法区分已完成、进行中或拿 operationId 轮询；也没有当前会话 signed-out 状态。测试只直接调用 use case，未经过 controller/HTTP/client contract。

### P1-2：所谓 integration 测试全部是内存 fake，未驱动真实仓储/Cloud Auth/组合根

`account-closure-coordinator.integration.spec.ts` 自建 `InMemoryAccountRepository`（[`account-closure-coordinator.integration.spec.ts:11`](../../packages/account/src/server/application/services/__tests__/account-closure-coordinator.integration.spec.ts:11)）、使用 `InMemoryAccountClosureOperationRepository`（[`account-closure-coordinator.integration.spec.ts:52`](../../packages/account/src/server/application/services/__tests__/account-closure-coordinator.integration.spec.ts:52)），revocation port 只是递增本地变量（[`account-closure-coordinator.integration.spec.ts:61`](../../packages/account/src/server/application/services/__tests__/account-closure-coordinator.integration.spec.ts:61)），publisher 只是 push 数组（[`account-closure-coordinator.integration.spec.ts:72`](../../packages/account/src/server/application/services/__tests__/account-closure-coordinator.integration.spec.ts:72)）。第二个恢复用例仍是同一组 fake。

它没有触达 `PrismaAccountClosureOperationRepository`、数据库唯一约束/并发 upsert、真实 `cloudAuthSession.deleteMany()`、Better Auth login/refresh、`AccountApiModule`、Electron module、HTTP middleware、真实 event bus/outbox 或跨进程恢复。unit 测试也只验证 mock 被调用（[`account-closure-coordinator.spec.ts:61`](../../packages/account/src/server/application/services/__tests__/account-closure-coordinator.spec.ts:61)）。2/2 通过不能作为生产 saga 接线证据。

缺失的关键测试至少包括：同 key 双并发 only-one-owner；同 key 不同 identity 拒绝；Prisma 中间 phase 崩溃与重启恢复；publish 后 crash 不重复消费；真实多 session/bearer/device code 失效；闭户后 login/refresh 拒绝；API/Desktop production composition 启动；后台 pending work fail-closed。

### P1-3：撤销认证与删除/保留数据没有独立审计政策

operation 只记录 phase/status/error/receipt（[`reliable-messaging.prisma:61`](../../packages/database/prisma/schema/reliable-messaging.prisma:61)），receipt 不记录 revoked session 数、认证主体动作、PII 清理结果、retention policy/version 或审计 actor。Coordinator 把事件 reason 固定成 `User requested closure`（[`account-closure-coordinator.ts:140`](../../packages/account/src/server/application/services/account-closure-coordinator.ts:140)），没有使用请求中的 reason/feedback，也没有明确哪些数据保留、匿名化或删除。

Cloud Auth 实现只做 session/device code 删除，业务 Account 只改 `Deactivated`；这可以是合理的分阶段策略，但代码和 receipt 没有把“立即安全撤权”与“受政策约束的数据删除/保留”建模成两个可审计阶段，无法核验隐私政策承诺。

### P2-1：phase/status 为自由字符串，缺少数据库级状态约束与恢复元数据

Prisma schema 的 phase/status 是任意 String（[`reliable-messaging.prisma:66`](../../packages/database/prisma/schema/reliable-messaging.prisma:66)），没有 enum/check、version、owner token、lease expiry、next retry/dead-letter 或 event id。TypeScript union（[`i-account-closure-operation-repository.ts:1`](../../packages/account/src/server/domain/repositories/i-account-closure-operation-repository.ts:1)）不能保护数据库被旧进程、手工操作或并发写入非法组合。该问题本身为 P2，但缺少 owner/CAS 已在 P0-2 构成放行阻塞。

### P2-2：默认幂等键包含自由文本 reason，协议和隐私边界不稳健

默认 key 直接拼接用户 reason（[`close-account.use-case.ts:26`](../../packages/account/src/server/application/use-cases/commands/close-account.use-case.ts:26)），既可能包含 PII/敏感自由文本并长期落在 unique index，也受空白、语言、文案变化影响。operation key 应是稳定、不透明、由协议明确携带或按 identity/closure generation 规范化生成的标识；reason 应进入独立受政策管理的审计字段，而不是兼任幂等键组成部分。

## 分级与放行决定

| 级别 | 数量 | 阻塞摘要                                                                                                                                                                                                                           |
| ---- | ---: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0   |    4 | API/Desktop composition root 不可启动且无真实 port wiring；saga 无条件写/并发所有权且 key 可跨 identity；requested 不阻断认证且 cloud identity 可重新登录；无 durable account-closed 发布/消费，后台 pending work 不 fail-closed。 |
| P1   |    3 | receipt 未贯穿 transport/客户端；integration 测试全部为内存 fake；认证撤权与数据删除/保留缺少独立审计政策。                                                                                                                        |
| P2   |    2 | schema 状态与恢复元数据约束不足；默认 key 包含自由文本 reason。                                                                                                                                                                    |

**终审判定：W3 第一轮不可进入第二轮。**

进入第二轮前至少应完成：

1. 由真实 API composition root 同时装配 Prisma closure repository、Cloud Auth revocation/disable adapter 和 durable event publisher；Desktop 若不拥有 cloud closure capability，应明确走远端关闭 port，而不是构造缺依赖的本地 Coordinator。
2. 将 repository 契约改为 identity-bound create/claim 和 expected-phase/version/owner 的条件转换，定义 running 接管/超时策略；同 key 不同 identity 必须拒绝，并用真实数据库并发测试证明 only-one-owner。
3. 在 requested 落库后立即让 sign-in、refresh、bearer/device flow 共享 closure deny policy；撤销全部 session/device code，并按明确政策禁用 cloud user/provider credential，防止重新登录。
4. 让 account close、operation phase 和 account-closed outbox 具备可证明的事务/幂等边界；事件携带稳定 eventId/operationId，下游使用 Inbox receipt，避免 domain event + publisher 双轨。
5. 让 closure receipt/idempotency key 进入公开契约，客户端可得到 running/succeeded/failed 与 signed-out 结果；补 API/Desktop composition、Prisma recovery、真实 Cloud Auth 多会话和 login/refresh 负向集成测试。

完成上述第一轮基础后，再实施第二轮的 `account-closed` consumer，并分别对 W1 Reminder、W2 Notification、Repository pending work 做 identity-scoped 条件取消、重复消费幂等和关闭后新 claim 拒绝。当前不应在非 durable publisher 上继续堆 consumer。

### 重点问题结论

1. **P0-3 sign-in/refresh**：不是“只在 coordinator 内调用”；API 的 closure repo 已真实注入 Cloud Auth，session create hook 能阻断新登录，principal resolution 也 fail-closed。但 `/api/auth/*` 原始 handler 没有统一 closure guard，缺少 session update/refresh hook；现有测试没有请求 sign-in/refresh endpoint。因此只能确认 sign-in 的 session-create 边界，不能确认 refresh/get-session 在 requested 窗口被阻断。
2. **P0-4 durable/lease/idempotency**：publish 确实落数据库，但 `closedAt` 不是稳定 event id；worker 没有 claim/lease/fencing、没有生产启动点。consumer 的 cancellation update 本身可重复执行，InboxReceipt 也有数据库唯一键，但这不能弥补 worker 双领、事件双写以及关闭后新 work 无门禁。
3. **P0-2 原子条件写**：repository 的单次 CAS 是真实原子写，并正确检查 affected 行数；问题在 coordinator 只对部分转换处理冲突，且 failed retry 仍以无条件 save 抢占。不能用“存在 CAS 方法”推导整个 saga only-one-owner。

### W0 冻结面与契约演进

`CloseAccountRes: null -> AccountClosureReceiptDTO` 是合理且必要的产品/API 演进，因为客户端需要 operationId、running/succeeded/failed 与 signedOut；该方向本身不构成回退。但当前改动没有记录为 W0 contract revision，也没有复用 W0 已冻结的 `AccountClosureReliableOperationPort -> BusinessOperationReceipt`（[`ports.ts:152`](../../packages/contracts/src/modules/reliable-messaging/ports.ts:152) 至 [`ports.ts:171`](../../packages/contracts/src/modules/reliable-messaging/ports.ts:171)）。W0 receipt 要求 schemaVersion/source/occurrenceKey、canonical idempotency key、lease、nextRetryAt/deadLetterAt 和统一状态不变量（[`operation-receipt.ts:270`](../../packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:270) 至 [`operation-receipt.ts:339`](../../packages/contracts/src/modules/reliable-messaging/operation-receipt.ts:339)），而新的 Account DTO 使用另一套 phase/status/attempts/timestamp 结构。故本轮应记录为**合理但尚未治理闭环的破坏性契约演进**：在 W3 收尾时要么正式 version/ADR 并定义与 W0 receipt 的映射，要么直接收敛到 W0 receipt；不能同时宣称 W0 frozen contract 与 Account 私有 receipt 都是 canonical。

### 重点问题结论

#### failed retry 的 CAS 接管

`status='failed'` 是有效的单语句原子守卫：两个 retrier 同时执行 `updateMany where status='failed'` 时，第一个把状态改为 running，第二个 count 为 0。因此第三轮描述的“两个 failed retry 只有一个 claim 成功”在 Prisma 语义上成立。

但这不能等同于 saga 已具备完整 fencing。phase CAS 把“当前 lease 已过期”也视为写权限，未要求调用者先成功 claim；外部副作用执行期间没有 heartbeat 或 phase-scoped claim；failure transition 也未检查 CAS 结果。真实 DB 测试没有覆盖 failed 双重试、lease 过期后旧 owner、慢副作用跨 lease 或 crash/restart。故第二轮的并发终审要求仍是 P0 未关闭。

#### Better Auth 原始路径

这轮确实不再只依赖业务 middleware：session create database hook 和 raw auth handler wrapper 都位于 `createCloudAuth()` 内。但 raw get-session closure deny 的新增测试实际失败，说明“进入 Better Auth 原始路径”不等于“原始路径已闭环”。当前 get-session 可返回被 closureChecker 判定为 closing 的有效 session，refresh 也没有独立 endpoint 证据；这是直接的认证 P0。

#### worker claim 与真实 consumer

worker 的 claim 本身是数据库 CAS，两个正常 worker 同时抢同一 pending row 时只有一个 token 能获得记录；稳定 eventId + consumer inbox transaction 也使重复消费有幂等基础。apps/api 新测试确实驱动了真实 Reminder/Notification consumer 类，而非纯 stub，因此这部分是有效进展。

不过测试没有启动生产 main/scheduler，Notification 路径未 seed/断言，Repository 完全缺席；worker completion/error write 也没有 owner fencing。最关键的是 main 当前 typecheck 不通过，所谓“生产接线”无法形成可发布产物。

### 契约与门禁

`CloseAccountRes` 从 null 改为 structured receipt，并已贯穿 controller、HTTP/IPC adapter 和 client port（[`account-lifecycle.dto.ts:24`](../../packages/contracts/src/modules/account/api/account-lifecycle.dto.ts:24) 至 [`account-lifecycle.dto.ts:43`](../../packages/contracts/src/modules/account/api/account-lifecycle.dto.ts:43)、[`account.controller.ts:79`](../../packages/account/src/server/transport/account.controller.ts:79) 至 [`account.controller.ts:89`](../../packages/account/src/server/transport/account.controller.ts:89)、[`account-api-client.port.ts:17`](../../packages/account/src/application-client/ports/account-api-client.port.ts:17) 至 [`account-api-client.port.ts:23`](../../packages/account/src/application-client/ports/account-api-client.port.ts:23)），成功/running receipt 不再被 transport 丢弃，这是合理修复。残余问题有两项：

1. Use case 将 failed receipt 转为普通 `Result` error（[`close-account.use-case.ts:35`](../../packages/account/src/server/application/use-cases/commands/close-account.use-case.ts:35) 至 [`close-account.use-case.ts:41`](../../packages/account/src/server/application/use-cases/commands/close-account.use-case.ts:41)），客户端仍拿不到 failed operationId/attempts/retryable/PII 状态。
2. Account 私有 receipt 仍没有版本化或映射到 W0 `BusinessOperationReceipt`，第二轮指出的 frozen contract 分叉没有关闭。

Reminder/Notification 增加 `./server` export 后，tsup 确实产出对应 server 文件，package-export-audit 与完整 governance-check 也通过；因此白名单改动在现有规则下是合法的。但两个 `server/index.ts` 都 `export *` 整个 infrastructure/domain，并非只暴露 account-closed consumer（[`server/index.ts:1`](../../packages/reminder/src/server/index.ts:1) 至 [`server/index.ts:7`](../../packages/reminder/src/server/index.ts:7)、[`server/index.ts:1`](../../packages/notification/src/server/index.ts:1) 至 [`server/index.ts:7`](../../packages/notification/src/server/index.ts:7)），属于为一个 composition symbol 扩大完整服务端公共面；而 account 自己没有 `./server` package export/tsup entry，API main 又错误地从 root 导入 API module/worker。结论是：**白名单更新本身可接受，但当前 package surface 组合不完整且过宽，不能用 governance 绿灯替代 API build/typecheck。**

### 测试真实性边界

### Findings

#### P0-1：marker 在不安全状态下被清除，云端成功后本地新工作会重新放行

marker 的安全清除条件不能只是“HTTP close 返回成功”，而必须是本地 Account 已可靠变为非 Active，或承载新工作的本地 runtime 已停止。当前顺序是 `DELETE marker -> remove token -> disable cloud sync`；既没有等待 PowerSync 把 Account 投影同步为 Deactivated，也没有 deactivate Profile。若 close receipt 返回时本地 Account 仍为 Active，删除 marker 后 Reminder/Notification checker 将同时得到“Active + no marker”并返回允许；随后云同步被关闭，这个 Active 投影还可能长期保持。marker 由临时窗口门禁变成了在最关键状态被提前撤销的门禁。

删除语句还没有按 identity 限定，会清空该 DB 中全部 marker；虽然当前 profile-per-DB 设计降低了误删概率，但它没有表达 checker 与清理目标必须是同一 identity 的契约。无论采用“保留 marker 直到本地 Account 非 Active”还是“先可靠停用 profile/runtime 再清理”，都必须补一项真实状态迁移测试，证明 cloud success 后不会出现 `Active + no marker + runtime active`。

#### P0-2：Desktop schedule-notification composition 缺 checker，Profile 注册会直接失败

`registerBusinessModules()` 在创建 schedule orchestration 时同步调用 `createNotificationPowerSyncScheduleNotificationPort(db)`。该 factory 直接 `new CreateNotificationUseCase(...)`，没有传入 closure checker；构造器则对缺失 checker 立即抛出 `[FAIL-CLOSED] CreateNotificationUseCase requires closureChecker`。因此这不是某个 schedule 到点后才暴露的边缘错误，而是 active Profile 业务模块注册阶段的确定性失败。

Notification 235 项绿测没有调用这个 factory；全仓也没有该 PowerSync schedule port 的测试。六审已要求 schedule notification 走同一 policy，本轮虽然为 `createNotificationPowerSyncModule()` 注入 checker，却漏掉了绕过 module factory、直接构造 use case 的 schedule port。

#### P0-3：closure marker 仍允许静默 no-op，云端请求前门禁不是强制契约

`closeCloudAccount` 缺失时 handler 会 fail-fast，但同等安全级别的 `markAccountClosing` 和 `afterCloudAccountClosed` 却仍为 optional 并通过可选链调用。已有“closes cloud first”测试甚至不提供 marker callback 仍期待成功，这固化了无 marker 也可发起云端关闭的旁路。canonical `markAccountClosing()` 又在取不到 identity 时静默返回；handler 在取得 token 前虽检查过一次 cloud identity，但经过异步 token 获取后再读取 descriptor，缺少把已认证 `identityId` 作为 marker key 传入并强制写成功的契约。

这违反六审已确认的 production checker 必填/fail-fast 原则。对云端 close 能力存在的 composition，marker writer 和安全完成 callback 应同样必填；写 marker 失败或 identity 不一致必须阻止云端 POST，而不是继续执行。

#### P1-1：新增测试只覆盖分离单元，未覆盖真实 Desktop closure 状态机

Account 顺序测试只验证三个 mock 的 invocation order，没有使用实际 profile DB、marker writer、HTTP promise 和 cleanup callback，也没有断言云端调用悬挂期间 create use case 被拒绝、云端失败时 marker 保留、云端成功后 runtime/Account/marker 的安全组合。Reminder/Notification checker 测试手工创建普通 SQLite 表；它们证明查询函数本身，但没有驱动 PowerSync schema 与 Desktop composition。Notification 版本还缺查询失败用例。

因此“mark before POST”和“checker sees marker”分别成立，不能推出同一真实 close 流程端到端成立；本轮两个 P0 正是分离测试之间的接线与生命周期缺口。
