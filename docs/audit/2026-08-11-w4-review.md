# W4 第一轮审查：Goal/Task 边界与持久化原子性

本次审查对照 [`2026-08-09-business-p0-elegant-fix-plan.md`](../plan/archive/2026-08-09-business-p0-elegant-fix-plan.md) W4，复核当前工作区未提交实现。审查只新增本文档；未修改业务代码，未 commit/push。

## 终审结论

**W4 第一轮不可放行：不要提交 W4，不进入 W5。**

当前没有发现 P0。Goal completed/archived 的重复调用已经做到不推进 version、不调用 repository save；Task create 已强制经过 transaction runner，Prisma/PowerSync runner 也把模板、实例和 eligible Goal outbox 放在同一事务回调内，生产 module 缺 runner 会 fail-fast。相关单测、集成测试、typecheck、build 和 governance 均通过。

但核心跨模块边界没有按 W0/W4 契约闭合：Goal 的 canonical Prisma/PowerSync factory 仍在 Goal 包内直接实例化查询 `taskTemplate/task_templates` 的 adapter，Task 包新增 adapter 没有被任何组合根消费；本轮还绕开 W0 已冻结的 `GoalDependencyReadPort`，另建了一套签名不同且不执行输入 schema 校验的 port。依赖检查也没有把 task binding count 作为结构化字段返回。终态测试只证明 aggregate 不再保存，未实现或验证 W0 `GoalReliableOperationPort` 的 durable completion receipt，因此“receipt 不再次写入”没有持久化证据。最后，`task:lint` 因遗留 unused inline-runner import 实际失败。

## Findings

### P1-1：Goal 仍直接拥有 Task ORM/SQL adapter，Task read port 是未接线的重复实现

W0 已冻结 `GoalDependencyReadPort.checkActiveTaskBindings({ identityId, goalId })`，输出包含 `hasActiveBindings/activeCount`（[`ports.ts:175`](../../packages/contracts/src/modules/reliable-messaging/ports.ts:175)）。本轮却在 Goal application 内另建 `ITaskBindingReadPort.findActiveBindingsForGoal(identityId, goalId)`（[`task-binding-read-port.ts:6`](../../packages/goal/src/server/application/ports/task-binding-read-port.ts:6)），既没有复用 frozen contract，也没有在边界执行 `GoalTaskBindingQueryInputSchema`。

更关键的是，Goal Prisma factory 直接构造 Goal 包内的 `PrismaTaskBindingReadPort`（[`prisma.ts:27`](../../packages/goal/src/server/infrastructure/prisma.ts:27)、[`prisma.ts:39`](../../packages/goal/src/server/infrastructure/prisma.ts:39)），该 adapter 直接访问 `db.taskTemplate.count`（[`prisma-task-binding-read-port.ts:4`](../../packages/goal/src/server/infrastructure/adapters/prisma/prisma-task-binding-read-port.ts:4)）。PowerSync factory 同样构造 Goal 包内 adapter（[`powersync.ts:27`](../../packages/goal/src/server/infrastructure/powersync.ts:27)、[`powersync.ts:39`](../../packages/goal/src/server/infrastructure/powersync.ts:39)），后者直接查询 `task_templates`。这仍是 Goal infrastructure 知道 Task persistence model，并不满足“不让 Goal 直接依赖 Task ORM”。

Task 包新增的 Prisma adapter 同时暴露两套方法且没有显式 `implements GoalDependencyReadPort`（[`prisma-task-binding-read-port.ts:3`](../../packages/task/src/server/infrastructure/adapters/prisma/prisma-task-binding-read-port.ts:3)）；全仓调用点搜索显示它和 PowerSync 对应实现只被 index export，没有生产消费者。结果是双轨重复 adapter，而不是 Task-owned read capability 被 host composition root 注入 Goal。

**要求**：保留一套 W0 frozen port；由 Task 提供明确实现并在 API/Desktop 的外层组合根注入 Goal，Goal 包删除所有 `taskTemplate/task_templates` ORM/SQL 知识。生产 factory 必须对缺失 capability fail-fast，不能在 Goal 内重新构造跨域 adapter。

### P1-2：删除依赖检查未结构化返回 task binding count

`checkDependencies()` 内部取得 `taskBindingCount`，但返回类型只有 `hasTaskLinks/canDelete/warnings`，没有 `taskBindingCount`（[`delete-goal.use-case.ts:33`](../../packages/goal/src/server/application/use-cases/commands/delete-goal.use-case.ts:33)、[`delete-goal.use-case.ts:76`](../../packages/goal/src/server/application/use-cases/commands/delete-goal.use-case.ts:76)）。计数只存在于中文 warning 字符串；execute conflict 也只把计数拼进英文 message（[`delete-goal.use-case.ts:105`](../../packages/goal/src/server/application/use-cases/commands/delete-goal.use-case.ts:105)）。调用方若要显示数量、埋点或做策略判断，只能解析文案。

删除阻断本身是 fail-closed 的：查询异常不会继续删除，count 大于 0 返回 `CONFLICT`，count 为 0 才执行带 expectedVersion 的 soft delete。Prisma 和 PowerSync 查询也都带 `identityId + goalId + deletedAt is null`。但 W4 的“返回计数/警告”要求尚未形成稳定结构化 contract。

**要求**：在正式 application/transport contract 中返回明确的 `taskBindingCount`（或直接复用 W0 `activeCount`），warning 仅用于展示；补 controller/client contract 断言。

### P1-3：只证明了 aggregate 幂等，未实现 durable completion receipt 幂等

Complete/Archive 在检查 expectedVersion 前识别终态并直接 materialize `GoalMutationReceipt`（[`complete-goal.use-case.ts:36`](../../packages/goal/src/server/application/use-cases/commands/complete-goal.use-case.ts:36)、[`archive-goal.use-case.ts:36`](../../packages/goal/src/server/application/use-cases/commands/archive-goal.use-case.ts:36)）。对应测试证明重复 complete 不增加 version/event 且不调用 save（[`complete-goal.test.ts:76`](../../packages/goal/src/server/application/use-cases/commands/__tests__/complete-goal.test.ts:76)），archive 测试证明不增加 version 且不调用 save（[`archive-goal.test.ts:60`](../../packages/goal/src/server/application/use-cases/commands/__tests__/archive-goal.test.ts:60)、[`archive-goal.test.ts:87`](../../packages/goal/src/server/application/use-cases/commands/__tests__/archive-goal.test.ts:87)）。这一部分成立。

但 W0 已冻结的 `GoalReliableOperationPort.recordGoalCompletionReceipt()`（[`ports.ts:200`](../../packages/contracts/src/modules/reliable-messaging/ports.ts:200)）在 Goal/Task/apps 中没有实现、注入或调用；当前 `GoalMutationReceipt` 只是每次从 aggregate 重新构造的返回 DTO。因而没有 durable receipt write，也无法验证首次终态提交与 receipt 的原子关系、重复请求不再次写 receipt、进程重启后返回同一 operation receipt。

**要求**：明确 W4 所称 receipt 的 canonical 类型。若按计划/W0 是 `BusinessOperationReceipt`，应接入 `GoalReliableOperationPort`，以 identity + source + occurrence 的 canonical idempotency key 持久化，并补首次写、重复不写、重启重放和失败回滚测试；不能用“本来没有 receipt write”宣称“receipt 不再次写入”。

### P1-4：Task lint 门禁实际失败

`CreateTaskTemplateUseCase` 已不再使用 inline fallback，但 import 仍保留 `createInlineTaskWriteTransactionRunner`（[`create-task-template.use-case.ts:19`](../../packages/task/src/server/application/use-cases/commands/create-task-template.use-case.ts:19)）。本轮实跑 `task:lint` 报 `@typescript-eslint/no-unused-vars` error，导致 goal/task 的 `test,typecheck,build,lint` run-many 总体失败。

这不改变“生产 create 强制 runner”的行为判断，但发布门禁不绿，不能提交放行。

### P2-1：跨 identity 只测了 mock，没有验证真实 adapter

DeleteGoal unit test 通过 mock 根据传入 identity 返回不同 count，证明 use case 会转发 identity；没有 Prisma/PowerSync read adapter 测试写入两个 identity 的同 goalId/binding 后验证隔离，也没有空 identity/schema 负向测试。由于本轮恰好新增跨域 SQL/ORM adapter，这属于 W4 明列验证项的证据缺口。

### P2-2：outbox 同事务的代码结构成立，但缺 outbox 故障注入

Prisma runner 在同一 `$transaction` callback 中创建事务绑定 repositories，并在 callback 返回前 append eligible `taskGoalOutbox`（[`prisma-task-write-transaction-runner.ts:25`](../../packages/task/src/server/infrastructure/adapters/prisma/prisma-task-write-transaction-runner.ts:25)、[`prisma-task-write-transaction-runner.ts:49`](../../packages/task/src/server/infrastructure/adapters/prisma/prisma-task-write-transaction-runner.ts:49)）；PowerSync runner 对应逻辑也位于同一 `writeTransaction` callback（[`powersync-task-write-transaction-runner.ts:25`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.ts:25)、[`powersync-task-write-transaction-runner.ts:32`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.ts:32)）。Create use case 的 template save 与 instance saveMany 均在 runner work 内（[`create-task-template.use-case.ts:51`](../../packages/task/src/server/application/use-cases/commands/create-task-template.use-case.ts:51)、[`create-task-template.use-case.ts:112`](../../packages/task/src/server/application/use-cases/commands/create-task-template.use-case.ts:112)）。静态上同 commit 成立。

现有 Prisma/PowerSync 测试注入的是 `saveMany` 失败，能证明 template/instances 回滚且 event 不发布（[`prisma-task-write-transaction-runner.integration.test.ts:119`](../../packages/task/src/server/infrastructure/adapters/prisma/prisma-task-write-transaction-runner.integration.test.ts:119)、[`powersync-task-write-transaction-runner.test.ts:205`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.test.ts:205)）；没有注入 outbox append/SQL 失败并断言 template、instances、outbox 全部回滚，也没有成功路径断言三者同 commit。应补这一故障矩阵以锁定 W4 不变量。

- Prisma/PowerSync transaction runner 均在 commit 后才 flush 非 outbox events；事务失败不发布 buffered events。

## 第二轮审查

本轮对照第一轮 4 个 P1 逐项复核当前工作区，并检查 API/Desktop 的真实注册入口、W0 frozen ports、Prisma receipt 集成测试与近邻门禁。审查只更新本文档；未修改业务代码，未 commit/push。

### 终审结论

**W4 第二轮仍不可放行：不要提交 W4，不进入 W5。**

第二轮修复关闭了原 P1-4，并完成了 P1-1 的大部分内部重构：Task-owned Prisma/PowerSync adapter 已显式实现 W0 `GoalDependencyReadPort`，输入经过 frozen schema 校验；Goal-local Task ORM/SQL adapter 已删除，Goal module 的两个 port 也改为必填且 fail-fast。Prisma lane 还新增了真实数据库集成测试，证明相同 canonical idempotency key 最终只有一条 outbox 记录。

但生产主路径存在新的启动阻断：API 与 Desktop 实际注册的 `GoalApiModule` / `GoalElectronModule` 都没有注入已经变成 fail-closed 的 Task capability，注册时必然抛错。原 P1-2 仍未修复，`taskBindingCount` 依旧只进入 warning。原 P1-3 也只完成了“成功后去重”的一半：Goal aggregate 保存与 Prisma receipt 写入是两个独立提交，PowerSync lane 使用进程内 Map，均不满足第一轮要求的 durable/atomic/restart receipt 闭环。

### 第二轮分级

| 级别 | 数量 | 摘要                                                                                                              |
| ---- | ---: | ----------------------------------------------------------------------------------------------------------------- |
| P0   |    1 | API/Desktop canonical Goal module 未注入必需 Task read capability，生产注册路径启动即抛错。                       |
| P1   |    2 | binding count 仍未结构化返回；completion/archive receipt 未与 aggregate 原子提交且 PowerSync receipt 不 durable。 |
| P2   |    3 | factory 参数在类型上仍可选；真实 binding adapter 缺跨 identity/schema 测试；receipt/outbox 失败故障矩阵仍缺。     |

### P0-1：API/Desktop 主模块入口未接线，fail-closed factory 使应用无法启动

Prisma factory 在缺少 `options.taskBindingReadPort` 时立即抛出 `FAIL-CLOSED`（[`prisma.ts:27`](../../packages/goal/src/server/infrastructure/prisma.ts:27)）；PowerSync factory 同样经 `requirePort()` 抛错（[`powersync.ts:29`](../../packages/goal/src/server/infrastructure/powersync.ts:29)）。但 API 真正注册到 `apps/api/src/main.ts` 的 `GoalApiModule` 仍只传 `runtimeContributions`，没有构造或传入 `PrismaTaskBindingReadPort`（[`module.ts:42`](../../packages/goal/src/api/module.ts:42)、[`module.ts:49`](../../packages/goal/src/api/module.ts:49)）。Desktop 真正注册到 `apps/desktop/src/main/main.ts` 的 `GoalElectronModule` 也只传 runtime contribution，没有传 `PowerSyncTaskBindingReadPort`（[`index.ts:61`](../../packages/goal/src/electron/index.ts:61)、[`index.ts:68`](../../packages/goal/src/electron/index.ts:68)）。

本轮确实给三个 AI adapter 和一个 host-restart integration test 补了注入，但这些不是 API/Desktop 的 canonical Goal module 注册路径。由于 factory 的 `options` 与 `taskBindingReadPort` 在 TypeScript 签名上仍标成可选，API/Desktop typecheck 也不能在编译期发现漏接线，错误被推迟到启动期。

**要求**：在 API/Desktop 实际 composition root 构造 Task-owned adapter 并注入 Goal；新增覆盖 `GoalApiModule.register()` 与 `GoalElectronModule.register()` 的启动/注册测试。factory 类型签名应表达必填 capability，运行时 fail-fast 作为第二道保护。

### P1-1（原 P1-2）：binding count 仍没有进入结构化 contract

`checkDependencies()` 已调用 W0 `checkActiveTaskBindings({ identityId, goalId })` 并读取 `activeCount`，但公开返回类型仍只有 `hasTaskLinks/canDelete/warnings`，没有 `taskBindingCount` 或 `activeCount`（[`delete-goal.use-case.ts:33`](../../packages/goal/src/server/application/use-cases/commands/delete-goal.use-case.ts:33)、[`delete-goal.use-case.ts:76`](../../packages/goal/src/server/application/use-cases/commands/delete-goal.use-case.ts:76)）。新增测试也只断言 boolean 与中文 warning，没有断言结构化 count（[`delete-goal.test.ts:182`](../../packages/goal/src/server/application/use-cases/commands/__tests__/delete-goal.test.ts:182)）。因此第一轮 P1-2 的最低条件没有完成。

此外测试文件还残留一个指向已删除 Goal-local port 的 type-only import（[`delete-goal.test.ts:7`](../../packages/goal/src/server/application/use-cases/commands/__tests__/delete-goal.test.ts:7)）；当前 Vitest 因 type erase 仍通过，ESLint 将其报告为 warning。这不是本项阻断根因，但说明旧双轨清理并不完整。

**要求**：把 `taskBindingCount`（或 `activeCount`）加入正式 application/transport 返回契约，并补精确数值断言；warning 保持纯展示用途。

### P1-2（原 P1-3）：Prisma 只证明成功后去重，receipt 仍非原子；PowerSync 仍非 durable

正向进展成立：Complete/Archive 都强制注入 `GoalReliableOperationPort`，使用 canonical idempotency key；Prisma adapter 在 `reliable_outbox_messages.idempotency_key` 唯一约束上做 find/create/race refetch；新增集成测试真实驱动 Prisma，重复 complete 后以 `findMany` 和 raw SQL 双重断言一行，且本轮实跑 4/4 通过（[`goal-prisma.repository.integration.test.ts:211`](../../packages/goal/src/server/infrastructure/adapters/prisma/goal-prisma.repository.integration.test.ts:211)）。

但首次完成仍先独立调用 `saveRootWithExpectedVersion()`，成功后才调用 receipt port（[`complete-goal.use-case.ts:64`](../../packages/goal/src/server/application/use-cases/commands/complete-goal.use-case.ts:64)、[`complete-goal.use-case.ts:74`](../../packages/goal/src/server/application/use-cases/commands/complete-goal.use-case.ts:74)）；Archive 同构。若 receipt create 失败，请求会报错但 Goal 已进入终态，首次终态提交与 receipt 并非原子。现有集成测试只覆盖两个调用都成功，没有注入 receipt 写失败并断言回滚，也没有创建新 Prisma client/module 来证明重启重放返回同一 operation receipt。

PowerSync factory 更直接注入 `InMemoryGoalReliableOperationAdapter`（[`powersync.ts:47`](../../packages/goal/src/server/infrastructure/powersync.ts:47)）；其状态只是实例内 `Map`（[`in-memory-goal-reliable-operation.adapter.ts:10`](../../packages/goal/src/server/infrastructure/adapters/in-memory/in-memory-goal-reliable-operation.adapter.ts:10)），模块重建或进程重启即丢失，并会为相同 operation 生成新的 `operationId`。它是单进程幂等 fake，不是 durable receipt 实现。

**要求**：让 Goal 终态 CAS 保存与 Prisma receipt/outbox 在同一 transaction-bound operation 中提交；补 receipt 写失败回滚、重启后同 receipt/operationId、archive 对称路径测试。PowerSync lane 必须使用本地持久化实现并覆盖模块重建/进程重启语义，不能以进程内 Map 作为生产可靠性 adapter。

### 已关闭与部分关闭项

- **原 P1-1 部分关闭**：Goal application 已复用 W0 frozen `GoalDependencyReadPort`；Task 包的 Prisma/PowerSync adapter 显式 `implements` frozen port 并执行 `GoalTaskBindingQueryInputSchema.parse()`；Goal-local ORM/SQL adapter 与 local port 文件已删除。未关闭部分由 P0-1（真实 host 漏注入）和 P2（真实 adapter 验证缺口）承接。
- **原 P1-4 已关闭**：本轮实跑 `task:lint` 为 86 warnings、0 errors，退出码 0；`goal:lint` 为 176 warnings、0 errors，退出码 0。Task 的 unused inline-runner error 已消失。

### 已关闭：第五轮 P2-2 PowerSync outbox 实例状态回滚非空证明

fake DB 的 `UPDATE task_instances` 分支现在从与生产 repository 一致的第四个 SET 参数读取 status，并写入 staged instance（[`powersync-task-write-transaction-runner.test.ts:161`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.test.ts:161)）。生产 SQL 的列顺序确为 `template_id, identity_id, instance_date, status, ...`，第四个参数就是 `data.status`（[`task-instance-powersync.repository.ts:40`](../../packages/task/src/server/infrastructure/adapters/powersync/task-instance-powersync.repository.ts:40)、[`task-instance-powersync.repository.ts:56`](../../packages/task/src/server/infrastructure/adapters/powersync/task-instance-powersync.repository.ts:56)）。因此 complete 在 outbox append 前会把事务快照中的实例真实改为 `Completed`。

fake 的 `writeTransaction()` 只在 callback 成功返回后才以 staged snapshot 替换 committed state；outbox INSERT 在 `failOutbox` 开启时抛错，赋值不会执行（[`powersync-task-write-transaction-runner.test.ts:68`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.test.ts:68)、[`powersync-task-write-transaction-runner.test.ts:105`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.test.ts:105)）。故障用例随后从 committed DB 状态重新查询同一 instance 并断言 `Pending`，同时断言 outbox 为 0、事件未发布（[`powersync-task-write-transaction-runner.test.ts:372`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.test.ts:372)、[`powersync-task-write-transaction-runner.test.ts:376`](../../packages/task/src/server/infrastructure/adapters/powersync/powersync-task-write-transaction-runner.test.ts:376)）。若失败路径错误提交 staged snapshot，该查询会读到 `Completed` 并失败；因此 Pending 已构成实例 mutation 回滚的非空证明。第五轮 P2-2 关闭。
