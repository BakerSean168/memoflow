# W2 审查：Notification channel capability 与 durable dispatch

本次审查对照计划 W2、根因判定表、实施依赖、风险/回滚和完成定义，复核当前工作区未提交的 W2 产物以及 W1 Reminder→Notification intent 对接。审查只新增本文档；未修改业务代码，未 commit/push。

## 结论

**W2 不可放行，不应提交 W2，也不能进入 W3。**

当前实现已经具备独立的 Notification dispatch outbox 表、创建通知时 aggregate/channel/outbox 的单事务写入、基础 conditional claim、receipt 映射和 identity 条件的 dead-letter adapter 方法；218 个单测、6 个集成用例和 typecheck 也确实通过。但生产 composition root 没有注册任何真实渠道 adapter，反而显式覆盖掉 Prisma module 的 durable runtime；W1 写入的 Notification intent 没有 W2 consumer；SSE 仍由 create use case 直接发布进程内事件；worker 的终态写没有 owner/fencing 条件，deliverer 也拿不到 deliveryId/idempotencyKey。上述问题直接命中计划第 68--70 行和完成定义第 134--137 行，不能以绿测放行。

## Findings

### P0-1：生产组合根没有真实渠道 capability，并绕过了 durable runtime wiring

`createNotificationPrismaModule()` 本来会创建 `NotificationReliableOperationPrismaAdapter`，并在未显式传入 runtime 时将 repository、reliable adapter 和渠道配置一起注入 worker（[prisma.ts:24](../../packages/notification/src/server/infrastructure/prisma.ts:24)、[prisma.ts:35](../../packages/notification/src/server/infrastructure/prisma.ts:35)）。但真实 API 注册路径显式传入 `createNotificationRuntimeContribution()` 的无依赖实例（[module.ts:39](../../packages/notification/src/api/module.ts:39)），从而使 `options.runtimeContributions ?? [...]` 选择左侧实例，完全绕过前述 durable adapter wiring。

该无依赖 runtime 在 production 会因为默认要求 InApp/Push 且 registry 为空而抛错（[notification.runtime.ts:105](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:105)），因此确实 fail-closed；但仓库内除 options 类型和测试 double 外没有任何 `NotificationChannelDeliverer` 实现或生产注册点。结果不是“生产 capability 已落实”，而是“生产必然无法启动”。在 development/test 中同一实例可构造成功，但既无 reliable adapter 也无 repository，`tick()` 没有工作分支（[notification.runtime.ts:145](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:145)、[notification.runtime.ts:332](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:332)），会静默启动一个不投递的 worker。

另外，调用方可仅声明 `channelCapabilities.status='available'` 通过启动检查，而 registry 中并不一定存在对应 deliverer；真正的缺失直到处理消息时才由 `getDelivererForChannel()` 发现（[notification.runtime.ts:91](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:91)、[notification.runtime.ts:128](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:128)）。这不是对实际 adapter 注册结果的 capability 校验。

这违反计划要求的“按渠道注册真实 adapter”和完成定义中的“所有 P0 有真实生产 capability”。

### P0-2：W1 Notification intent 与 W2 worker 使用两张互不相通的 outbox，Reminder→Notification 闭环未对接

W1 在 Reminder 的事务中写入通用 `OutboxMessage`，`messageType='notification.dispatch'`，payload 内包含 W0 Notification intent（[prisma-reminder-write-transaction-runner.ts:123](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:123)、[prisma-reminder-write-transaction-runner.ts:146](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:146)）。该表映射为 `reliable_outbox_messages`（[reliable-messaging.prisma:9](../../packages/database/prisma/schema/reliable-messaging.prisma:9)）。

W2 worker 只调用 `claimOutboxDispatch()`（[notification.runtime.ts:149](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:149)），而该 adapter 只查询 `NotificationDispatchOutbox`（[notification-reliable-operation-prisma.adapter.ts:151](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:151)），对应另一张 `notification_dispatch_outbox` 表（[notification.prisma:116](../../packages/database/prisma/schema/notification.prisma:116)）。全仓搜索没有 `notification.dispatch` 的生产 consumer，也没有把 `OutboxMessage` 原子/幂等转换为 Notification aggregate、channel 和 `NotificationDispatchOutbox` 的桥接逻辑。

即使补一个直接转发表，W1 当前 channel 值为 `'in-app'`（[prisma-reminder-write-transaction-runner.ts:136](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:136)），W2 registry/创建用例使用枚举值 `'InApp'`（[notification.runtime.ts:84](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:84)、[create-notification.use-case.ts:79](../../packages/notification/src/server/application/use-cases/commands/create-notification.use-case.ts:79)），仍需统一协议而不能直接投递。

因此 W1 写出的 intent 会永久停在通用 outbox，Reminder P0 可靠投递闭环未成立。

### P1-1：worker 的完成写丢失 lease/fencing，旧 owner 可覆盖新 owner，重复投递无法被阻止

claim 本身使用 `id + fencingToken + 可领取状态` 的 conditional update，基本竞争路径正确（[notification-reliable-operation-prisma.adapter.ts:176](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:176)）。但 worker 在成功、retryable 和 dead-letter receipt 中都先把 `lease` 改为 `null`（[notification.runtime.ts:216](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:216)、[notification.runtime.ts:261](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:261)、[notification.runtime.ts:297](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:297)）。`recordDeliveryReceipt()` 只有 receipt 仍带 lease 时才附加 `claimId/fencingToken` 条件；lease 为 null 时退化成 operation id 条件（[notification-reliable-operation-prisma.adapter.ts:297](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:297)）。它也不校验 owner、running 状态或 lease 未过期。

worker 从未调用已实现的 `heartbeatLease()`。如果外部投递超过 30 秒，或投递成功后在 receipt 写入前崩溃，第二 owner 会在 lease 过期后重新 claim 并再次调用渠道；旧 owner 随后还可无条件覆盖新 owner 状态。deliverer 接口只收到 aggregate 与 channel，不接收 outbox `operationId`/`idempotencyKey`（[notification.runtime.ts:24](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:24)），真实渠道 adapter 无法用 W0 delivery key 做下游去重。

数据库 `idempotencyKey @unique`（[notification.prisma:125](../../packages/database/prisma/schema/notification.prisma:125)）只能防止重复插入 intent，不能证明“重复消费不重复投递”。

### P1-2：SSE 不是 outbox consumer，断线后也没有 receipt 恢复入口

创建用例在数据库保存返回后直接调用 `pushSSEEvents()`（[create-notification.use-case.ts:140](../../packages/notification/src/server/application/use-cases/commands/create-notification.use-case.ts:140)、[create-notification.use-case.ts:151](../../packages/notification/src/server/application/use-cases/commands/create-notification.use-case.ts:151)），并通过进程内 event bus 同步发布 in-app/desktop 事件（[create-notification.use-case.ts:165](../../packages/notification/src/server/application/use-cases/commands/create-notification.use-case.ts:165)）。异常被记录后吞掉（[create-notification.use-case.ts:201](../../packages/notification/src/server/application/use-cases/commands/create-notification.use-case.ts:201)）。worker 成功写 receipt 后没有发布 SSE outbox event 或推进 SSE consumer cursor。

普通 notification list 可以重读 aggregate，但 ApplicationPort/HTTP routes 没有 delivery receipt/list timeline 查询；routes 仅有通知 CRUD、未读数和偏好（[routes.ts:72](../../packages/notification/src/api/routes.ts:72)、[routes.ts:174](../../packages/notification/src/api/routes.ts:174)、[routes.ts:235](../../packages/notification/src/api/routes.ts:235)）。因此客户端断线后无法按 receipt 判断 pending/running/retryable/dead-letter，也无法恢复漏掉的实时 delivery event。计划要求的“SSE 只是 outbox consumer，断线可从 receipt/list 恢复”未实现。

### P1-3：dead-letter/replay 只有 infrastructure runtime 方法，不是授权的运维接口

Prisma adapter 的 query 确实按 `identityId + dead_letter` 过滤，replay 首次读取也按 `identityId + operationId + dead_letter` 过滤（[notification-reliable-operation-prisma.adapter.ts:338](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:338)、[notification-reliable-operation-prisma.adapter.ts:354](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:354)）。这证明了 adapter 层 identity fence。

但它们只被 runtime 对象包装（[notification.runtime.ts:410](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:410)），没有进入 `NotificationApplicationPort`、module API、controller 或带 `auth/requireRole` 的 routes；API composition root 也没有保留 runtime 的运维 facade。当前没有调用者可用且可授权的 dead-letter 查询/replay 运维接口，不能满足计划所称“按 identity 授权”。

### P1-4：状态/指标闭环不完整，仍保留非 durable 双轨 dispatch

durable 路径会写 succeeded/retryable/dead-letter receipt 并计数 dispatched/delivered/failed/retry/dead-letter；但 metrics service 的 `recordPersisted()` 没有任何调用点，`persistedTotal` 永远为 0（[notification-metrics-service.ts:22](../../packages/notification/src/server/domain/services/notification-metrics-service.ts:22)）。指标只是 runtime 进程内计数器，没有生产 telemetry exporter/注册点；API 实际绕过该 runtime 后也无法观察这些计数。

当 `reliableAdapter` 缺失但 repository 存在时，worker仍会走旧的 channel 状态扫描路径（[notification.runtime.ts:332](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:332)）。该路径不产生 `BusinessOperationReceipt`，失败/重试/dead-letter 只写 aggregate channel 和内存指标。这是计划第 119 行要求删除的长期双轨行为，不能作为生产或通用 fallback 保留。它没有恢复旧的 no-op deliverer 假成功，但仍绕过 W0 receipt/outbox/lease 不变量。

### P2-1：schema 与实现存在脆弱的 notificationId 推导和自由状态字符串

repository/adapter 并未让 input 显式携带 `notificationId`，而是用 `occurrenceKey.split(':')[0]` 推导外键（[notification-prisma.repository.ts:150](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-prisma.repository.ts:150)、[notification-reliable-operation-prisma.adapter.ts:98](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:98)）。这只适用于当前 create use case 的 `${notification.id}:${channel}` 约定，不适用于 W1 的 `${templateId}:${time}` occurrenceKey，也把不透明 occurrence key 当成可解析结构。schema 的 `status/channel/source` 均为自由字符串（[notification.prisma:121](../../packages/database/prisma/schema/notification.prisma:121)），放大了 `'in-app'`/`'InApp'` 一类协议漂移。

## W1 一致性

W1 与 W2 都使用 W0 canonical idempotency key/receipt 类型，这是契约层的一致点；W1 的 intent 也带 identity/source/occurrence/channel/payload/idempotencyKey。但持久化与消费层不一致：W1 写 `OutboxMessage`，W2 读 `NotificationDispatchOutbox`；没有 inbox receipt/consumer 将前者转换为 Notification aggregate 和后者，也没有对 `OutboxMessage.status` 做 dispatched/failed/dead 更新。channel 命名也不一致。**W1 intent → W2 worker 的实际对接为未实现。**

## 6 个集成用例真实性

集成文件实际有 6 个 `it()`（[notification-reliable-operation.integration.test.ts:64](../../packages/notification/src/server/infrastructure/adapters/prisma/__tests__/notification-reliable-operation.integration.test.ts:64) 至 [notification-reliable-operation.integration.test.ts:264](../../packages/notification/src/server/infrastructure/adapters/prisma/__tests__/notification-reliable-operation.integration.test.ts:264)），本地实测 6/6 通过，但覆盖声明需严格限定：

1. 用例 1 先手工 seed Notification，再单独调用 adapter `dispatchOutbox()`；证明 receipt/表写入，不证明 aggregate/channel/outbox 原子性。
2. 用例 2 证明重复**入队**返回同一行，不调用 worker/deliverer，不能证明重复**消费**不重复投递。
3. 用例 3 的两个 `Promise.all` claim 能证明首次 claim 基本互斥；没有并发执行外部 deliver + 终态写。
4. 用例 4 证明过期 lease 可被新 owner claim；没有让旧 owner 在抢占后完成 receipt 写，未覆盖 stale-owner fencing 缺口，也不是 SSE 断线恢复。
5. 用例 5 直接把 pending receipt 手工改为 dead_letter，再顺序 query/replay；没有错误 identity 负向断言、真实失败重试、角色授权或 replay 后实际投递。
6. 用例 6 证明成功创建后 aggregate、两个 channel 和两个 outbox 都存在，并走一次 happy-path tick；没有在 outbox/channel 写入点注入异常证明整体回滚，也没有模拟 commit 后崩溃、重复 tick 或 downstream idempotency。

fail-fast 覆盖位于 unit spec 而非这 6 个集成用例（[notification-durable-dispatch.spec.ts:18](../../packages/notification/src/server/infrastructure/runtime/__tests__/notification-durable-dispatch.spec.ts:18)），且测试手工传入 capability 状态，不启动真实 `NotificationApiModule`。所有新增 worker metrics 单测都走无 reliable adapter 的旧 repository fallback（[notification-durable-dispatch.spec.ts:63](../../packages/notification/src/server/infrastructure/runtime/__tests__/notification-durable-dispatch.spec.ts:63)）。没有 W1→W2 端到端、生产 composition root、SSE 断线/list receipt 恢复、适配器超时/权限拒绝、重复消费、stale owner completion 或 replay 不重复发送测试。

## 边界与回滚核验

- 业务变更集中在 Notification runtime/use case/repository/schema、必要的 `Account` ORM 反向关系、generated Prisma client、测试 target/inventory；未发现 W3 账号关闭或其他业务 work package 的实施。`Account.notificationDispatchOutboxes` 是 Prisma 双向 relation 所需，不视为越界业务逻辑。
- `project.json` 大部分 diff 是格式展开，generated Prisma client 体积较大，增加审查噪声但不是本次不可放行根因。
- 旧 no-op deliverer 假成功已经删除；但 API development 空 worker、直接 SSE best-effort 和 repository-only dispatch 双轨仍属于隐式降级/绕过 durable receipt 的可达路径。
- schema 使用新增表而未删除 W1 通用 outbox，回滚可以停止 worker并保留两类历史；但当前没有 W1 consumer，所谓“停 worker、保留 intent 后人工 replay”的计划回滚能力尚不可操作。

## 分级与放行决定

- **P0**：P0-1 无真实生产 channel adapter 且 API composition root 绕过 durable runtime；P0-2 W1 intent 与 W2 worker 没有 consumer/表级对接，Reminder→Notification 可靠链路中断。
- **P1**：终态 receipt 写丢失 lease/fencing且无运行中 heartbeat；deliverer 不接收幂等键，重复消费可重复发送；SSE 仍是 create use case 的进程内 best-effort；dead-letter/replay 无授权 application/API 入口；persisted 指标未记录且 telemetry 未接入；repository-only 非 durable 双轨仍可达；测试未覆盖这些关键不变量。
- **P2**：notificationId 从 occurrenceKey 字符串拆分、状态/channel 自由字符串导致协议脆弱；配置/generated diff 噪声。

**最终决定：W2 不可放行。不要提交 W2，不进入 W3。** 至少需要先接通 W1 `notification.dispatch` consumer；在真实 API composition root 注册并校验实际 channel adapters 与 durable worker；让所有 worker 状态写保留 owner/fencing/expiry 条件并把 idempotencyKey 传至渠道 adapter；把 SSE 改为可重放 consumer并提供 receipt/list 恢复；暴露带身份/角色授权的 dead-letter/replay；补齐 persisted telemetry，以及真实 composition、跨模块、断线、故障注入和重复消费测试后再复审。

## 第二次审查

审查日期：2026-08-10。审查范围为第二次迭代对一审问题的修复，并回归 W2 已有的事务 outbox、worker claim/lease 和数据库唯一幂等能力。本节结论以当前工作区代码和本轮实跑结果为准。

### 终审结论

**W2 仍不可放行。**

第二次迭代确实补上了 worker 三条结果路径的 owner/fencing 条件写，条件失败会返回数据库中的现有 receipt；create use case 也不再直接广播 SSE；dead-letter、replay 和 receipt timeline 已进入 application port、controller 与认证路由，`persisted` 计数也有实际调用点。但这些修复尚未满足 W2 的端到端不变量：外部投递发生在 fencing 完成写之前且 deliverer 不接收 idempotency key，失租并发仍会重复发送；SSE 广播仍是 receipt 写入后的非持久进程内副作用，没有消费游标或补发标记；新增测试没有覆盖真实 HTTP 认证、错误 identity、SSE 断线补发或 replay 与仍在执行的旧 owner 竞态。

### 新问题与竞态

#### P0：生产组合根仍无真实渠道 adapter

`NotificationApiModule` 已不再用无依赖 runtime 覆盖 Prisma module，这是相对一审的 wiring 修正；但它仍未向 Prisma module 传入 `channelDeliverer/channelDeliverers`。当前 production 的实际结果是启动时因 InApp/Push 缺失而失败，不是计划要求的“按渠道注册真实 adapter”。同时 runtime 仍保留缺少 reliable adapter 时直接扫描 repository 的非 durable fallback（[notification.runtime.ts:394](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:394)），违反实施顺序要求的“最后删除旧 fallback”。

#### P1：SSE 存在不可恢复的 commit→broadcast 丢失窗口

当前没有独立 SSE outbox/consumer 状态。成功 receipt 一旦提交，dispatch outbox 变为 succeeded，不会再被 claim；若随后的进程内广播未发生，服务端 receipt/list 虽可查询最终状态，但客户端无法重放对应实时事件。这不是带游标的增量消费，也没有证据证明客户端重连会调用 receipt timeline 并补齐 UI。

#### P1：replay 与旧 in-flight owner 的竞态仍可重复发送

`replayDeadLetter()` 的 `dead_letter → retryable` 条件更新使并发 replay 请求本身只有一个状态转换获胜（[notification-reliable-operation-prisma.adapter.ts:414](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:414)），后续 claim 也受 fencing 保护；这一部分正确。但 lease expiry 后的旧 owner 可能仍阻塞在外部 deliverer，新 owner可以失败并写 dead-letter，人工 replay 又可启动下一次投递，而旧 owner 最后仍可能完成外部发送。现有 deliverer 契约和测试均不能对该跨 owner/in-flight 场景去重。

### 新问题：跨实例顺序与 replay 原子性

#### P1：SSE 游标不具备跨实例一致性或全序

数据库 receipt 是共享的，因此客户端若始终携带一个有效 timestamp，任一实例理论上都能执行一次增量查询；这不等于 consumer cursor 持久化。服务端游标状态是每实例私有 `Map`，live event bus 也是进程内对象。更严重的是 `updatedAt` 不是唯一游标：多个 worker/事务可以产生相同时间戳，查询使用严格 `gt`，一旦一批结果在相同 timestamp 处被 limit 截断，后续请求会永久跳过同 timestamp 的剩余行。当前没有 `(updatedAt, operationId)` 复合顺序、数据库 event sequence 或 consumer offset，不能证明多 worker 下无丢失、无乱序。

#### replay 条件更新本身原子，但不覆盖外部副作用原子性

`replayDeadLetter()` 先读后写不是理想的单语句返回实现，但决定状态转换的 `updateMany` 同时检查 identity/status/lease 并自增 fencing，因而两个并发 replay 不会都完成 `dead_letter -> retryable`。失败方重读当前行也不会覆盖赢家。此处**没有新增数据库原子性 P1**。

原子性边界止于数据库：replay、claim 和 completion 都不能与外部 channel send 形成同一个事务。正确性仍依赖下游以稳定 deliveryId/idempotencyKey 去重，或等价的渠道 inbox/fence；当前 deliverer 契约没有该信息。因此“replay 状态原子”不能推导出“replay 不重复发送”。

### 新问题与一致性核验

#### 共享 consumer 与 Reminder worker 不会领用同一行，但共享 consumer 自身不可恢复

全仓调用点显示 Reminder worker 不读取或 claim `OutboxMessage`；它只在 occurrence 的事务内创建 `notification.dispatch` 行（[prisma-reminder-write-transaction-runner.ts:123](../../packages/reminder/src/server/infrastructure/adapters/prisma/prisma-reminder-write-transaction-runner.ts:123)）。因此“Notification consumer 与 Reminder worker 同时领用同一表/同一行”的直接竞争**不存在**：前者是消费者，后者是生产者。

真正的竞争发生在多个 Notification runtime 之间。`id + status + attempts` CAS 能保证 pending/retryable 的首次领用互斥，但 schema 没有 lease owner/expiry，任何 worker 在 `running` 后崩溃都会让消息永久不可再领；也没有 stale completion fence。该实现不满足任务明确要求的共享 outbox lease/claim，更不能由“没有 Reminder 竞争者”推导为可靠。

#### P1：InApp 持久化、receipt 与 SSE 广播次序不一致且重复广播

durable worker 调用 `RealInAppChannelDeliverer.deliver()` 时，deliverer 先保存 aggregate 并立即广播；返回后 runtime 才把 channel 标为 delivered、写 succeeded receipt、再次保存 aggregate，再由 `NotificationSseAdapter` 广播同一个 in-app 事件（[notification.runtime.ts:212](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:212)、[notification.runtime.ts:268](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:268)、[notification.runtime.ts:276](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:276)）。结果是一次 dispatch 至少可产生两个实时事件；第一个事件发生时 receipt 仍为 running、列表中的 channel 也可能仍为 Pending。若第一次 save 失败，adapter 还会吞错并广播。

W1 路径另有 id 分裂：新建 aggregate 的真实 id 由 domain factory 生成，但后续 receipt/SSE payload 使用另一个随机 `notifId`（[notification.runtime.ts:423](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:423)、[notification.runtime.ts:431](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:431)、[notification.runtime.ts:482](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:482)）。列表对象、实时事件和 receipt 因而可能引用不同 notification id。当前不能证明计划要求的“in-app 列表与实时事件最终一致”。

#### P1：旧的非 durable fallback 与外部幂等缺口仍在

reliable adapter 缺失时直接扫描 repository/channel 的旧 fallback 仍可达（[notification.runtime.ts:526](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:526)），继续绕过 W0 receipt/outbox/lease。`NotificationChannelDeliverer` 接口也仍只接收 aggregate/channel，不接收稳定 deliveryId/idempotencyKey；测试 10 证明的是首次并发 claim，不覆盖 lease expiry、进程崩溃、旧 in-flight owner 或 replay 后的外部调用去重。

#### P1：新增 SSE route 违反 typed event bus 治理门禁

本轮实跑 governance 并未通过。`routes.ts` 直接调用 raw `eventBus.on()`/`off()`（[routes.ts:321](../../packages/notification/src/api/routes.ts:321)、[routes.ts:324](../../packages/notification/src/api/routes.ts:324)），被 `raw-event-bus-audit` 明确拒绝；应使用仓库规定的 typed subscriber。背景中“governance 通过”的陈述与当前工作区不符，完成定义所要求的发布门禁未满足。

### 遗留阻塞与本轮新问题

#### P0：默认生产 adapter 仍不具备可确认的真实 capability

`RealInAppChannelDeliverer` 仍捕获并吞掉任意 repository save 异常，之后照常发布事件并 resolve（[real-channel-deliverers.ts:25](../../packages/notification/src/server/infrastructure/adapters/deliverers/real-channel-deliverers.ts:25)）。Desktop/Push adapter 仍只向当前 Node 进程的 singleton event bus 发布 desktop event（[real-channel-deliverers.ts:50](../../packages/notification/src/server/infrastructure/adapters/deliverers/real-channel-deliverers.ts:50)），而实际 native notification listener 位于 Electron main 进程（[notification.service.ts:214](../../apps/desktop/src/main/services/notification.service.ts:214)）。API 与 Desktop 不共享进程内 bus；Push 还被映射到同一个 Desktop adapter。生产 capability presence check 因对象存在而通过，但无法证明副作用可达或可确认，仍违反完成定义。

#### P0：W1 shared consumer 修正了 FK，但仍会在 durable fence 前产生副作用且崩溃不可恢复

共享 `OutboxMessage` schema 仍没有 owner、claim、lease expiry 或 fencing 字段，虽然仓库已经有 `InboxReceipt`，该 consumer 并未使用（[reliable-messaging.prisma:9](../../packages/database/prisma/schema/reliable-messaging.prisma:9)、[reliable-messaging.prisma:31](../../packages/database/prisma/schema/reliable-messaging.prisma:31)）。claim 只将候选从 pending/retryable CAS 到 `running`（[notification-reliable-operation-prisma.adapter.ts:480](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:480)）；进程在此后崩溃会永久卡住，completion 也只按 id 更新。runtime 仍先调用 deliverer、标记 channel 并保存 aggregate，之后才创建/取得 dispatch receipt（[notification.runtime.ts:451](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:451)、[notification.runtime.ts:462](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:462)、[notification.runtime.ts:466](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:466)）。因此“外部发送成功后、receipt/shared status 前崩溃”仍会在人工恢复或未来重领时重复发送；测试 12 只证明 FK/id 正确，没有故障注入这个窗口。

#### P1：SSE port 修复治理语法，但没有建立无丢失的 durable subscription 边界

route 的 catch-up query 发生在 live subscribe 之前（[routes.ts:298](../../packages/notification/src/api/routes.ts:298)、[routes.ts:313](../../packages/notification/src/api/routes.ts:313)）；两者之间完成的 receipt 既不在已结束的 query 中，也可能早于 subscriber 注册，形成明确丢失窗口。cursor 仍是非唯一 timestamp，`updatedAt > cursor` 配合单字段排序和固定 limit 100 会在同毫秒碰撞或积压超过一页时永久跳过事件。port 背后仍是进程内 global event bus，因此实时段不跨实例。

此外，默认 InApp deliverer 在 durable receipt 写入前发布一次 event，worker 在 receipt 写入后又由 SSE adapter 发布一次（[real-channel-deliverers.ts:33](../../packages/notification/src/server/infrastructure/adapters/deliverers/real-channel-deliverers.ts:33)、[notification.runtime.ts:268](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:268)、[notification.runtime.ts:276](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:276)）。route 经 port 会同时收到两类事件，所以“SSE 只是 outbox consumer”在生产 composition 下仍不成立；用例 11 注入 no-op mock deliverer，避开了这条生产双广播路径。

#### P1：既有外部幂等与非 durable fallback 缺口仍在

`NotificationChannelDeliverer.deliver()` 仍只接收 aggregate/channel，不携带 deliveryId/idempotencyKey（[notification.runtime.ts:31](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:31)），数据库 fencing 无法阻止 lease expiry 或 replay 后旧 in-flight owner 的外部重复发送。reliable adapter 缺失时的 repository channel scan fallback 仍可达（[notification.runtime.ts:533](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:533)），继续绕过统一 receipt/outbox/lease，违反计划规定的“最后删除旧 fallback”。

#### P2：port 化引入 duck typing、silent no-op 与 transport 命名泄漏

`NotificationApplicationPort` 直接暴露 `NotificationSseDeliveryEvent` 和 `subscribeSseEvents()`（[notification.application.port.ts:9](../../packages/notification/src/server/application/notification.application.port.ts:9)、[notification.application.port.ts:43](../../packages/notification/src/server/application/notification.application.port.ts:43)）；module 实现再通过 `as unknown`/`'getSseAdapter' in rc` 探测 infrastructure runtime，找不到 adapter 时静默返回 no-op unsubscribe（[notification.module.ts:258](../../packages/notification/src/server/infrastructure/notification.module.ts:258)）。这让 transport 协议进入通用 application port，也绕开了可静态检查的明确 runtime capability。它不是本轮单独的 P0，但属于 port 化新增的抽象泄漏，应改成显式注入、强类型且 fail-closed 的 subscription/cursor port。

#### P2：用例 11 仍有结构性时序风险；用例 12 未发现时序 flake

用例 11 在 `http.get()` 后没有等待服务端 route 完成 subscriber 注册，便立刻写 event 1 并执行 `runtime.tick()`（[notification-reliable-operation.integration.test.ts:573](../../packages/notification/src/server/infrastructure/adapters/prisma/__tests__/notification-reliable-operation.integration.test.ts:573)、[notification-reliable-operation.integration.test.ts:590](../../packages/notification/src/server/infrastructure/adapters/prisma/__tests__/notification-reliable-operation.integration.test.ts:590)）；首次 event 理论上可跑在订阅建立之前。断线后又用固定 `setTimeout(20)` 代替等待服务端确认 close/unsubscribe（[notification-reliable-operation.integration.test.ts:608](../../packages/notification/src/server/infrastructure/adapters/prisma/__tests__/notification-reliable-operation.integration.test.ts:608)）。本轮额外 5 轮均通过，尚未观察到实际 flake，但同步条件不显式，CI 负载下仍有风险。用例 12 的关键顺序均由 awaited DB 操作和 `runtime.tick()` 驱动，本轮 5 轮未发现时序风险。

### exactly-once 副作用语义专项判断

当前实现满足的是“**在调用渠道前持久化唯一 delivery intent**”，不满足通用的“**外部副作用 exactly once**”。`NotificationDispatchOutbox.idempotencyKey` 唯一约束能防止重复创建任务，claim/terminal write 的 owner+fencing 条件也能防止旧 owner 覆盖数据库终态；但它们不能撤销或确认已经发生的外部副作用。要闭合 `deliver success -> receipt commit` 窗口，真实渠道必须以传入的 idempotencyKey 做下游幂等/ack，或把副作用与 receipt 放进同一原子事务。当前 InApp/desktop 实现均未使用 context，且 InApp 还在 receipt 前广播。因此本轮不能宣称 exactly-once，最多是数据库任务的 at-least-once + conditional completion。

任务说明所称的“崩溃后 lease 过期可重领”只在 `NotificationDispatchOutbox` 的基础 lease 用例中有覆盖（[notification-reliable-operation.integration.test.ts:172](../../packages/notification/src/server/infrastructure/adapters/prisma/__tests__/notification-reliable-operation.integration.test.ts:172)）；没有测试 shared `OutboxMessage` claim 后崩溃，也没有测试 deliverer 已产生副作用但 receipt 尚未提交的窗口。两者不能混为同一个 exactly-once 证明。

### 新问题与 fail-fast / SSE 分页专项

1. **P1：reliableAdapter “fail-fast” 实际被 worker 自己吞掉。** 默认生产 composition 当前会注入 adapter，因此没有误伤默认正常路径；但 `runtimeContributions` override 可以替换掉默认 durable contribution（[prisma.ts:58](../../packages/notification/src/server/infrastructure/prisma.ts:58)），而 runtime 构造/start 都不拒绝，只有后台 tick 留一条日志。这既不是 fail-fast，也会把错误配置伪装成启动成功。
2. **P1：SSE 的 repository 全序查询没有传递到协议游标。** 复合查询本身可避免同时间戳遗漏，但 route 和 `NotificationSseAdapter` 仍把 cursor 降级为 `updatedAt`（[notification-sse.adapter.ts:92](../../packages/notification/src/server/infrastructure/adapters/sse/notification-sse.adapter.ts:92)），且没有 nextCursor/page loop；101 条积压必然只发送首 100 条，同时间戳下还会重复或跳过，取决于客户端最后保存的纯时间戳。
3. **P2：dead-letter 行的 lease owner 清理不一致。** `recordDeliveryReceipt()` 的 terminal 集合不包含 `dead_letter`（[notification-reliable-operation-prisma.adapter.ts:366](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:366)），所以 dead-letter completion 会清 claim/expiry 却保留 ownerToken（[notification-reliable-operation-prisma.adapter.ts:401](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-reliable-operation-prisma.adapter.ts:401)）。replay 会再次清理，暂不阻塞主链路，但会留下误导性的 owner 状态和审计数据。
4. **P2：注释/测试名称强于真实保证。** runtime 注释声称 shared lease 有 owner token、SSE 先订阅再补发（[notification.runtime.ts:151](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:151)），实际实现分别是 `availableAt` 和 query→subscribe；当前集成测试仍只有 12 个，未出现任务说明所列的崩溃窗口、竞态、碰撞和分页用例。后续验收应以可观测故障注入和真实生产 adapter 调用次数为准。

### 终审结论

**W2 仍不可放行，不应提交 W2，也不能进入 W3。**

本轮确实闭合了若干具体缺口：InApp 持久化失败会抛出且 deliverer 不再提前广播；InApp 把稳定 `deliveryId/idempotencyKey` 写进渠道 response，形成 receipt 之前的 durable ack；shared schema 和 claim 已增加 owner/claim/fencing/expiry；HTTP SSE 已改为 subscribe-before-query、本进程事件缓冲去重、复合 cursor 和循环分页；runtime 构造/start 也会拒绝缺少 reliable adapter。18 个通知集成用例、218 个单测、Notification typecheck 及 Reminder 26 个集成用例均实跑通过。

但两个 P0 仍未达到生产语义。第一，默认 composition 把没有 transport、每次调用都必然抛错的 Desktop/Push deliverer 注册为“available”，启动检查只看对象存在，因此生产不会在必需 capability 实际不可用时 fail-fast。第二，shared completion adapter 只有在调用方传入 lease 时才附加 owner/claim/fencing 条件，而生产 runtime 的所有完成调用都没有传 lease；过期旧 owner 仍可把新 owner 的 `running` 行改为 succeeded/retryable/dead-letter。SSE 也只消除了单进程 query/live 窗口：订阅仍基于进程内 event bus，历史查询结束后由其他实例落库的 receipt 不会到达当前连接。模块虽定义了 durable runtime 类型，实际仍通过方法属性探测选择实现，未满足“显式注入、无 duck typing”。

### exactly-once 与 shared 条件写专项

InApp 的成功副作用是 Notification/channel 的数据库持久化。deliverer 先把稳定 idempotency context 写入 channel response，再保存 aggregate；若进程在这次保存之后、receipt 更新之前崩溃，重领 worker 会重新读取 aggregate，并根据 status/response 跳过 deliverer。因此这不是“副作用和 receipt 同事务”，但确实是符合任务允许条件的 durable ack，新增用例 14 也真实验证了这个顺序。

该保证不能外推到整个 W2。Desktop/Push 没有可确认 transport/ack；而 shared `OutboxMessage` 的最终状态与其 lease 不是原子约束，因为 runtime 丢弃了 claim 得到的 ownerToken/claimId/fencingToken。具体竞态为：旧 owner 失租，新 owner 把同一行重新 claim 为 `running`，旧 owner随后调用未带 lease 的 `updateSharedOutboxStatus()`；其 `WHERE` 只有 `id + status=running`，会成功清掉新 owner lease并覆盖状态。故 shared outbox 的“conflict 不覆盖”只存在于可选 API 分支，不存在于生产调用链，P0-2 不能以 adapter 能力或绿测放行。

### 显式注入改造副作用与新增问题

本轮发现一个未被 218 个单测、19 个 Prisma 集成用例或 typecheck 覆盖的 **P0 Desktop 启动回归**。Electron composition 仍无参调用 `createNotificationRuntimeContribution()`（[electron/index.ts:105](../../packages/notification/src/electron/index.ts:105)），而该工厂现在在构造入口立即要求 `reliableAdapter`，缺失会同步抛出 FAIL-FAST（[notification.runtime.ts:164](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:164)）。PowerSync factory 只提供三个 repository 与 runtime contribution，不提供 durable adapter/port（[powersync.ts:36](../../packages/notification/src/server/infrastructure/powersync.ts:36)）。因此 `NotificationElectronModule.register()` 会在创建 module 之前失败，Desktop 通知 IPC 无法注册。这里不是合规的“生产 capability 缺失时拒绝投递”，而是 composition root 没有为 Desktop 选择可用的 durable runtime 实现。

### in-memory 兜底语义与 capability 一致性

`InMemoryNotificationReliableAdapter` 的类注释确实写明“专用于 Desktop / Electron 及单元测试场景（明确标示非持久化）”（[in-memory-notification-reliable.adapter.ts:111](../../packages/notification/src/server/infrastructure/adapters/in-memory/in-memory-notification-reliable.adapter.ts:111)），但 PowerSync composition 的公开注释仍称其为 `durable runtime`，没有在调用点或正式文档说明进程退出会丢失 outbox、receipt、lease、dead-letter 和 replay 历史（[powersync.ts:35](../../packages/notification/src/server/infrastructure/powersync.ts:35)）。这与 W2 的 durable dispatch、断线恢复和“回滚保留 operation/audit 历史”不是同一保证，不能仅靠实现类内部一行注释外推为可接受的生产边界。

更直接的不一致是：PowerSync factory 声明 Desktop `available`，真实 deliverer 却因未注入 transport 报 unavailable；runtime 没有被该声明欺骗，故 production 正确 fail-closed，但也因此没有修复 production Electron 注册。development 环境不会执行 production capability 拒绝，却仍因 PowerSync repository 与 in-memory adapter 无 enqueue 接线而只获得一个空 worker。若 Desktop 本地 lane明确不承担 durable dispatch，应提供不宣称 Desktop available 的显式 client-only port，并在架构文档说明 receipt/worker 由服务端 ownership；若它承担本地 dispatch，则必须把 outbox 持久化到 PowerSync/SQLite 并注入真实 Electron transport。当前实现两种边界都没有成立。

## 第十次迭代 — Desktop Durable Worker 架构设计说明

根据 Alex 决策，桌面 Electron 端采用架构决策 A **Desktop Durable Worker** 模式（持久 SQLite outbox + 真实 Electron transport）。

### 1. Owner 归属与数据库契约

- **桌面端独立 Outbox 存储**：Electron 主进程通过 `PowerSyncNotificationReliableAdapter` 直接绑定本地 PowerSync/SQLite 数据库 (`IElectronDatabase`)。该 Adapter 维护独立的 SQLite `notification_dispatch_outbox` 表。
- **Outbox 入队**：`PowerSyncNotificationRepository.save(notification, outboxDispatches)` 在同一 SQLite 事务中落库 Notification 聚合根、`notification_channels` 渠道行与 `notification_dispatch_outbox` 投递意图。

### 2. 崩溃恢复与 Lease/Claim 语义

- **SQLite 持久化**：Outbox 消息不使用 in-memory 队列，主进程崩溃或重启后消息仍然完好保存在 SQLite `notification_dispatch_outbox` 表中。
- **W0 Lease/Claim 重新领用**：桌面 worker 依据 W0 lease 语义（`ownerToken`、`claimId`、`fencingToken`）执行 `claimOutboxDispatch`。未完成且租约已过期的 `running` 消息或 `retryable` 消息在进程重启后会被新的 claim 成功领用，避免重复入队与死锁。

### 3. Deliver → Receipt 闭环与 Transport Ack

- **真实 Transport 注入**：`RealDesktopChannelDeliverer` 注入 Electron 桌面 transport（`createDefaultElectronDesktopTransport`，封装 Electron `Notification` API 与 IPC 广播）。`isAvailable()` 返回 `true`，满足生产环境 capability 检查。
- **Ack 持久化**：`RealDesktopChannelDeliverer` 执行 transport 后接收可确认的 `ack` 凭证（含 `ackId`、`status: 'delivered'`、`timestamp`），写入 `ChannelResponse.success` 并保存到 `notification_channels` 实体 response 字段中。
- **终态 CAS 写入**：`PowerSyncNotificationReliableAdapter.recordDeliveryReceipt()` 使用 `ownerToken` 与 `fencingToken` 条件更新 SQLite outbox 状态为 `succeeded` 终态，并清理 lease，完全闭合 deliver → receipt 窗口。

### 4. 与服务端 Prisma Runtime 的边界

- **服务端 Runtime**：基于 Prisma + PostgreSQL 的 `NotificationReliableOperationPrismaAdapter`，负责 API / Web 侧的 durable dispatch。
- **桌面端 Runtime**：基于 PowerSync + SQLite 的 `PowerSyncNotificationReliableAdapter`，负责 Electron 桌面端的 durable dispatch。
- **统一 API 协议**：桌面端与服务端底层 Adapter 均无缝实现 W0 契约 `NotificationReliableOperationPort`，保证跨层语义完全对齐。

### Desktop transport ack 与 exactly-once 专项

Desktop happy path 中，deliverer 会把 transport 返回对象放进 `ChannelResponse.success(...).data.ack`，随后 runtime 可将 notification channel 保存到 `notification_channels.response`；新增用例对 `ack-test-123` 的断言证明这一条无故障路径成立（[notification-powersync-durable-worker.spec.ts:241](../../packages/notification/src/server/infrastructure/adapters/powersync/__tests__/notification-powersync-durable-worker.spec.ts:241)）。但它不是可确认投递语义：默认 transport 在没有调用原生 `show()` 时也生成 ack，且没有校验 ack 的结构或 `status`。

持久化顺序也没有闭合崩溃窗口。runtime 先把 dispatch outbox 条件写成 `succeeded`，之后才调用 repository 保存已变更的 channel response（[notification.runtime.ts:403](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:403)、[notification.runtime.ts:407](../../packages/notification/src/server/infrastructure/runtime/notification.runtime.ts:407)）。若进程在两步之间崩溃，重启后 outbox 已是终态、不再 claim，而 `notification_channels.response` 仍为空。反向窗口中，transport 副作用已经发生但 outbox receipt 尚未成功时，Desktop transport 本身也没有使用 `deliveryId/idempotencyKey` 做持久去重。故“ack 持久化”和 Desktop exactly-once 只能描述当前 happy path，不能作为崩溃语义保证。

### PowerSync/SQLite 与 Prisma adapter 语义一致性

两套 adapter 在专用 dispatch 的字段映射、pending/retryable/过期 running claim、owner/fencing 条件终态写、dead-letter/replay 和 receipt cursor 形状上基本对齐；Prisma/server 既有语义未回退。但以下差异阻止“完全对齐”的架构结论：

1. Prisma 创建 aggregate/channel/outbox 使用 `$transaction()`（[notification-prisma.repository.ts:54](../../packages/notification/src/server/infrastructure/adapters/prisma/notification-prisma.repository.ts:54)），PowerSync repository 没有使用已存在于 `IElectronDatabase` 的 `writeTransaction()`，所以中间任一步失败会留下部分 aggregate、部分 channel 或无 outbox。
2. PowerSync shared outbox claim 的 retry/running 可用时间检查读取 `next_available_at`（[power-sync-notification-reliable.adapter.ts:779](../../packages/notification/src/server/infrastructure/adapters/powersync/power-sync-notification-reliable.adapter.ts:779)），但 completion 更新的是 `available_at`（[power-sync-notification-reliable.adapter.ts:854](../../packages/notification/src/server/infrastructure/adapters/powersync/power-sync-notification-reliable.adapter.ts:854)）；Prisma 两处统一使用 `availableAt`。因此 PowerSync retryable 行的 backoff 可被忽略，shared consumer 语义不一致。
3. 新 SQLite 测试预建全部目标表，且其 `writeTransaction()` 不执行真实事务；它证明 SQL happy path 可运行，不证明 production PowerSync schema、rollback 或重启恢复。

contracts 和 domain 的合法值集合已经同时包含 `Desktop`，Zod create/preference response schema会自动接受该值，Prisma 字段为 String，不存在数据库枚举迁移问题。运行时 normalize/registry 也能识别 `Desktop`，主投递路径类型没有断裂。

### 重点专项判断

1. **用例 20 是真双 runtime、真 `tick()`。** A 的 tick promise 被 deliverer gate 阻塞；B 在 lease 有效和人工过期后分别真实 tick；最终 A 的 completion 经过 runtime→adapter 条件写被拒绝。该测试已关闭九/十审指出的“adapter 直调冒充 runtime”问题。
2. **`writeTransaction()` 真正包裹全部业务写。** notification upsert、channel upsert 与 dispatch outbox 去重/insert 都只使用 callback 的 `tx`；任一步抛错会触发测试 wrapper 的 `ROLLBACK`。`ensureTablesExist()` 的幂等 DDL 位于事务前，不属于一次 notification aggregate/outbox commit 的业务状态写。
3. **transport ack 已 fail-closed。** 无 Electron capability、`show()` 抛错、无可调用方法、undefined/null/failed/missing-ackId 都不会形成 succeeded receipt。剩余 P0 不是 silent-success 回退，而是成功副作用之后缺少跨崩溃幂等/恢复协议。

## 第十二次审查

审查日期：2026-08-10。审查对象为任务说明所称的 W2 第二十五、二十六次迭代。本轮逐条核验十一审剩余 2 个 P0，专项检查两个新增 Desktop 崩溃故障注入是否真的跨进程/跨 store 恢复，并回归十审 schema/事务、fail-closed ack、双真实 runtime 竞态和 Prisma 集成用例 20。结论以当前工作区生产组合根、持久化 SQL、测试实际调用链和本轮实跑结果为准；类名中的 `Durable`、内存 Map、注释和绿测数量不替代崩溃后可重建的持久证据。

### 终审结论

**W2 仍不可放行，不应提交 W1+W2，也不能进入 W3。**

API bootstrap 缺口已经真实关闭：`apps/api/src/main.ts` 不再注册默认 singleton，而是在真实白名单组合根中调用 factory，并显式只声明 API lane 自治拥有的 InApp capability；runtime 又会把声明与实际 deliverer registry 交叉核验，声明本身不能伪造 adapter。因此 Desktop/Push 归 Desktop lane 的架构决策 A 已落实到生产组合根，而不再只是 module context 的可选字段。

Desktop transport 也确实开始消费稳定 `idempotencyKey`，同一 store 中已有 delivered ack 时会跳过 native `show()`；runtime 也新增了从 succeeded outbox 查询 ack 并补写 channel response 的投影。不过 production `PowerSyncDesktopTransportAckStore` 并没有能在目标崩溃窗口中独立落库的 ack 记录：它只有进程内 Map，所谓 durable 写只是尝试更新尚无 response 的 `notification_channels` 行，匹配条件又依赖 response 已包含该 key 或随机 channel id 包含该 key，首次成功 ack 时通常更新 0 行且不检查 `rowsAffected`。进程重启后新 store 只能从 channel response 反查，恰好无法恢复“show 已成功、channel response 尚未保存”的窗口。两个新增故障用例都复用同一 module、transport 与内存 Map，没有关闭并重开数据库/重建 store，所以不能证明 durable dedupe 或真实重启恢复。
